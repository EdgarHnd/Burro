# Burro

A small native macOS monitor for Git worktrees and Codex / Claude Code agents, with a live agent panel at the camera notch. Built with SwiftUI, Swift 6, a bundled Rust log worker, and system libraries. Requires macOS 14 or newer. Monitoring needs no additional accounts or hooks; optional usage limits use your existing provider sign-ins. Local monitoring stays on this Mac; remote monitoring uses SSH only for machines you explicitly add.

## Run

```sh
./script/build_and_run.sh
```

Source builds require Swift 6 and Rust through rustup; the repository pins the Rust toolchain. The script builds `dist/Burro.app` and its Rust helper, preserving the existing signing identity (ad-hoc on fresh setups without a certificate). You can launch that bundle directly or copy it to Applications. Other modes: `--build-only`, `--verify`, `--debug`, `--logs`, `--telemetry`.

```sh
./script/build_rust_worker.sh
BURRO_REQUIRE_RUST_WORKER=1 swift test
swift run burro-inspect --agents            # fast agent status, including unread results
swift run burro-inspect                     # JSON snapshot, automatic discovery
swift run burro-inspect /path/to/repository # limit to specified repositories
```

## Agent notch

Local Codex log inspection and Claude delegated-worker discovery/lifecycle parsing run in a private Rust child process, which reuses parsed lifecycle summaries while a file is unchanged. The app still checks live writer locks and event age on each poll. If that child fails, the existing Swift reader takes over and a later poll can restart it. Unverified chats remain protected and appear in Monitoring details, with a count in the notch footer. The active queue omits these rows by default; “Include idle and unverified chats” can show them alongside active chats. There is no separate service to install or configure; the worker exits with Burro.

- The notch is enabled by default. **Hover** over the black strip at the top of the screen to expand it; **click** to open or close; use the **pin button** to keep it open. Move away to collapse an unpinned panel, or use its chevron to collapse explicitly.
- **Agents / Usage** tabs stay visible in the expanded notch. Click a tab to keep it selected, including after closing and reopening the panel during this app session. Hover the other tab for 160 ms to preview it without changing your selection; move away to return. A Preview label and outlined tab distinguish temporary content. Quick crossings do not switch views; clicking during a preview commits it. Collapse/Escape clears any preview, while pinning keeps its existing meaning.
- A steady glow along the compact notch’s lower rim signals attention: **amber for input requests**, **blue for unread completed chats**. Input takes priority when both exist. The glow remains until the provider reports that input is handled or the result is read; hovering the notch does not acknowledge it. It uses short fades without pulsing, switches immediately with Reduce Motion, and adds no extra mouse-catching area. It follows both local and connected remote agents even when Usage is selected.
- The compact notch has two consistent status indicators: running agents on the left (waveform), and attention on the right (inbox: needs input plus Done/unread). It has no logo, name, or idle count, and a side whose count is zero stays empty (until the first check, both show "–"). Amber means some attention is input-related; blue means unread completions only. The expanded summary shows the breakdown. When nothing is running but a task is scheduled, the left indicator becomes a teal clock and scheduled count.
- The expanded list groups chats by machine and checkout path (not branch or folder name), with explicit folder and branch labels. Unavailable remote branch metadata is labeled unavailable. Local checkout Git delivery uses cached refs and is never attributed to a single chat. Grouping preserves every visible active/read-only chat, true unread Done results, and parent/worker links; workspace identities stay fixed during pointer interaction. Within that grouping, the list prioritizes **Needs you → Done/unread → Running**, then uncertain activity, Scheduled, and recent activity. The large title and repeated count are removed; up to five complete rows fit. The options menu can include idle chats, refresh status, or open monitoring details. Done results remain until the provider marks them read; merely opening the notch never acknowledges them.
- Codex workers with an explicit parent ID are folded beneath their parent chat. Others, including Guardian runs without that metadata, appear in a collapsed **Background workers** group per machine. Worker input requests promote the group and remain visibly labeled. Counts still represent unique agents, including working/waiting children; grouping does not discard safety evidence or infer ownership from a shared folder. Claude sessions without explicit parent metadata remain separate chats.
- While the pointer or keyboard focus is in the expanded panel, list positions and worker membership stay fixed; titles/status update live. New/disappearing items reconcile after interaction ends, or when **Update list** is chosen. A disappeared row is disabled rather than replaced under the pointer. Selecting a different filter deliberately refreshes the list.
- Click a chat to open it on Burro's Chats page. Hold ⌥ while clicking, or right-click → **Open in Codex** / **Open in Claude**, to open it in the provider's app instead; right-click → **Show in Burro** opens its details. **Settings → Agent notch → Open chats in Burro** (on by default) swaps the two: off, a click opens the provider's app and ⌥ opens Burro. A chat without a provider link always opens in Burro. Expand a worker group to open a specific worker. The footer arrow opens worktrees.
- The separate read-only agent poll runs independently of Git scanning: about 3 seconds after each sample while a chat is active or uncertain, and every 15 seconds when everything is quiet and the file watcher is running (file changes still wake it at once). A problem reading a provider's unread state is reported but doesn't keep the poll at 3 seconds. Footer notices name the affected machine and distinguish history coverage from connection failures. Click a notice for details, last successful remote check, and retry. Unknown/recent is not reported as confirmed running.
- Placement prefers the MacBook's notched display and reserves the camera's physical width. On every display, the black surface attaches flush to the physical top edge, including displays without a camera notch. Concave shoulders and rounded lower corners make it part of the screen edge, with no floating-window shadow. Layout updates when displays or Spaces change; the nonactivating panel joins other apps’ fullscreen Spaces and remains above them without switching apps or bringing the dashboard forward. It stays on your configured notch display; other displays do not get duplicate indicators.
- Hover opens immediately, including an 8-point approach area around the compact strip. The expanded panel has a 10-point edge tolerance and closes 120 ms after leaving. Returning cancels closing immediately. Passive pointer-movement observers work over Burro and other apps, independent of view tracking areas. Core Animation animates the outline and content fades, preserving motion through reversals while text stays at a fixed size. Deliberate collapse stays closed until the pointer leaves and returns. Opening with a click or keyboard does not silently pin the panel.
- Settings and the menu bar let you disable the notch or prefer the main display. **⇧⌘B** opens it while Burro is active. It does not install a global keyboard shortcut or request accessibility/input-monitoring permissions. Clicking inside the panel does not activate the dashboard unless you choose an agent/worktree link.
- The notch deliberately uses a black surface to blend with the camera housing, with restrained sage and amber accents. It respects Reduce Motion and keeps monitoring when the dashboard closes.

Chat navigation uses `codex://threads/<UUID>` and Claude's existing desktop/bridge session IDs. These are navigation-only links: opening one does not send a prompt, import/resume a CLI session, or change remote access settings (replies are a separate, explicit action in [Chats](#chats)). Bare Claude CLI sessions without desktop/bridge metadata open their Burro details. Exact Code-session routes were checked against the installed apps; private provider routes can change. See [Claude's URL scheme documentation](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) for the public deep-link overview.

### Home

The Burro window opens on **Home**. Everything on it comes from the same live feed as the notch: **running**, **need you** (input requests) and **to read** (unread Done results).

- **The cover**: a greeting, then chips for the running count and, only when there is something, **N need you** (amber) and **N to read**; each opens Chats. Under them, the plain-language summary, when the agents were last checked and a button to check now.
- **What needs you**, directly under the cover: each chat waiting on you is an amber row (avatar, title, machine · folder) that opens the chat; up to five show, then **Show all N in Chats**. Results ready to read are one quieter line, **N ready to read**, that opens Chats. With nothing waiting it says **Nothing needs you**.
- **Cards**: the Orchestrator's [Brief](#the-brief), your main project, then benches, projects and machines as flat, monochrome cards; colour comes only from their live-count pills, and an unreachable machine's tile is greyed. Projects are your repositories plus any folder holding an active chat; each card shows live chats, worktree count, folders ready to clean and today's tokens. Machines are this Mac and each remote you added. Click a project for its worktrees, this Mac for Mac Health and another machine for Machines.

"Tokens today" counts local Codex and Claude logs on this Mac since midnight, read by the bundled Rust worker in the background while Home is on screen (at most every 90 seconds). It is an estimate, like the Usage page's local history, and is hidden if the worker is unavailable. Home samples Mac Health only while visible and starts no other polling; worktree inventories refresh on opening Home or Worktrees under the same rules as before.

Use the top bar or **⌘1–⌘8** for Home, Orchestrator, Today, Chats, Worktrees, Machines, Usage and Mac Health. **⌘R** refreshes the current page. **Settings → Appearance** chooses Match System, Light or Dark; the notch always stays dark.

### Home and navigation

The window has its own top bar (drag it to move the window; double-click to zoom), with **Home**, the **Orchestrator** (it pulses while it works) and **Today** on the left, in ⌘1–⌘3 order, and on the right **Chats** (badge: chats that need you or have results to read; amber while any chat needs you, blue when there are only results to read), **Worktrees**, **Machines**, **Usage**, **Mac Health** (badge: leftover processes) and **New chat**. The current page's icon widens into a pill with its name. ⌘1–⌘8 jump to Home, Orchestrator, Today, Chats, Worktrees, Machines, Usage and Mac Health.

- **Back and Forward**: ⌘[ and ⌘] (also in the **Go** menu) step through the pages you've shown, like a browser. When you reach a page from inside another (opening a chat from Today or Home, say) rather than from the top bar, a shortcut or the menu bar, a **‹ Today**-style back pill appears after the left icons and returns to where you started; the Timeline shows **‹ Today** too.
- **⌘K** (**View ▸ Command Palette…**) opens a search over the main window: pages, every chat on every machine (the Chats list), projects and machines, plus a few actions: **New chat…** (or **New chat in** a project, which opens the New chat sheet with it selected; **New chat on <Machine>…** and **New chat in <folder> on <Machine>…** for your other machines, listed below this Mac's), **Start chat: "…"** for whatever you typed (it opens the New chat sheet with that text as the prompt; it is the only row when nothing else matched, otherwise the last), **Open Settings**, **Refresh** the current page, **Keep awake for 2 hours** (or **Stop keeping awake**) and **Ask the Orchestrator about** a chat, which puts the question in the Orchestrator's composer without sending it. Type to filter; chats that need you rank first, then working chats. ↑/↓ move, Return runs, Escape or a click outside closes it. Nothing in it messages or starts an agent by itself. When the Notes window is in front, ⌘K is its own action list.
- **Window ▸ Burro** (⌘0) reopens the window after you close it; the notch and menu bar keep running without it. Clicking Burro in the Dock does the same.
- **Menu bar**: the Burro icon alone when nothing is running, the icon and a count while agents run, and a needs-you glyph with the number waiting while a chat needs you (menu-bar items have no colour). The menu shows the counts, lists up to five chats waiting on you, newest first (choosing one opens it like a notch row: in Burro, or in its provider app with ⌥ or with **Open chats in Burro** off), then **N drafts ready** when the Orchestrator has replies drafted for you to send (it opens Home, where the Brief shows them; the menu-bar label doesn't count drafts), and has **Show Agent Notch**, **Notes**, **Enable Notch**, **Keep Awake**, **Open Burro**, **Open Today**, **Open Chats**, **Refresh** and **Quit Burro**.

Home sits on an ASCII aquarium that stays put while the page scrolls over it. Your agents are the fish. The species comes from provider and model: Claude Opus is a shark, Fable a sailfish, Sonnet a barracuda and Haiku a minnow; Codex's Sol models are tunas, Astra models angelfish and other GPT models pufferfish. Subagents are small fry that swim beside their parent. Effort sets the variety: low effort darts about with small plain fins, while higher effort glides slower with longer fins, stripes at Extra High and spots at Max (or Ultra). Size is age: a new chat starts as a small fish and grows over its first day. A chat that needs you turns amber and waits at the surface. Scheduled chats, waiting on a timer, are jellyfish that drift almost in place and pulse; their tentacles grow longer with effort. Every other chat from today (idle, done or closed) swims too, darker, so the tank shows the whole day; up to 24 fish, 16 fry and 5 jellyfish, with chats that need you or are working first. Hover a fish or jellyfish in the open water between cards to see its chat, model, effort and age, and click it to open the chat. Model and effort come from Codex's thread index and the end of Claude's transcript, so they show only when the provider records them. The tank animates a few frames a second, only while Home is on screen, and holds still with Reduce Motion. The photo button switches to a glyph or pixel field or a photo (any image or your desktop picture) across the top instead. Below the cover and what needs you: the Orchestrator's **Brief**, your **main project**, project and machine cards (a quiet tile, the name, live counts or "Quiet"), and on the right **To-dos**, **Today so far** (with activity tracking on), **Notes** (click + or a note to open it in the Notes window) and a **Scratchpad** that saves as you type. The floating dock shows avatars in three groups, running, needs you (amber) and to read (blue), each opening its chat, then the **+** New chat button and shortcuts to the notch, Today, refresh and Settings.

### Startup and notifications

**Settings → Startup → Open at login** makes Burro a login item. When macOS opens it at login, Burro starts quietly: the notch, menu bar and activity tracking run, but it doesn't come to the front or show its window. Click Burro in the Dock, open it again, or use the notch, menu bar or ⌘0 to bring the window back. Burro tells a login launch from a normal one by the launch event macOS sends.

**Settings → Notifications** has two switches, both off: **Notify when a chat needs you** and **Also when a chat finishes**. Turning one on asks macOS for permission; if it's turned off in System Settings, the section says so with **Open Notification Settings…**. A banner is posted once per chat when it has been waiting on you (a question or an approval, on any machine) for about 5 seconds, or, with the second switch, when a chat Burro saw working finishes with a result to read. The banner names the provider, folder and machine, and the chat's title; it is removed once the chat stops waiting or the result is read. A needs-you banner goes out without waiting for the Orchestrator; when [triage](#the-brief) later writes a headline for that chat, a banner still on screen is replaced in place, quietly, with "<title>: <headline>". Click it to open the chat on the Chats page. A chat that is already waiting the first time Burro sees it (at launch, when a remote machine connects, or when one comes back after being unreachable or after sleep) doesn't notify until it leaves that state and comes back, and a machine dropping out doesn't withdraw a banner or post it again. Subagents never notify, and banners left over from a previous run are cleared when Burro starts. Notifications only read chat state; they need the bundled app.

### Main project

Home features one project: the repository with the most worktrees, or the one you choose from the card's **⋯** menu. The card shows how many chats are running or need you in it on every machine, its worktrees, folders ready to clean and today's tokens, a **Live** column (working, waiting and unread chats) and **Earlier today**. **New chat** opens the New chat sheet with that project selected; **Worktrees** filters the worktree list to it. It is left out of the project grid below.

### Chats

**⌘4** (or the chat icon in the top bar) lists every Codex and Claude chat Burro sees, on this Mac and your SSH machines: **Needs you**, **Working**, **Ready to read** and **Recent**, with chats you pinned at the top of their section. Under each title is its machine and folder, shown once for a run of chats in the same folder, and the chat's last reply when Today's activity scan has already read it (Burro doesn't read each chat's file just for the list). Chats you just started appear in a **Starting** group above the others until the real chat shows up (see [New chat](#new-chat)). Search matches titles, folders and machine names. Pick a chat to read it. A long opening brief (like a session another chat started) shows as a **Task** card with **Show more**. Each turn shows your message, then a **Worked for 3m 9s** line that stays open while the chat works: the agent's notes, runs of tool calls folded into one line such as **Ran 5 commands, read 2 files** (open it for each call; click a call for its output), delegated subagents on their own line, and the plan as a checklist card (done, in progress, to do). Then comes the reply with Markdown, code blocks, and any images or videos the agent linked (`![caption](/path/file.mp4)`). Media on this Mac loads in place; from another machine, images up to about 8 MB copy over SSH automatically, and larger images and videos when you click (see [Other laptops and servers](#other-laptops-and-servers) for where copies are kept). Click an image to open it. **Open in Codex/Claude** appears when the provider has a link.

**Following a live chat.** While a chat is working or waiting and on screen, Burro re-reads it every 2 seconds on this Mac (every second while a reply you sent isn't in its log yet) and every 4 seconds on another machine. On this Mac the Rust worker parses only what the file added since the last read, so an unchanged chat costs almost nothing; on another machine only the new bytes travel (see below). The page follows new messages while you're at the bottom; scrolled up, it stays where you are and offers **↓ N new**. While the chat works, a strip at the bottom says what it's doing right now, using the tool call's own description when it gave one, and for how long. When the chat waits on you, **Jump to last question** (⌘↑) scrolls to it. A reply you send shows at once, dimmed as **Sending…**, until the chat's own log has it (an echo the log never shows within a few minutes is dropped, as is one whose send failed).

**Reply** from the composer at the bottom. Return sends, ⌥Return adds a line. Each option starts as "keep what this chat uses":

- **Access**: Ask me, **Approve for me** (Codex reviews its own approval requests), Edit freely, or Read only.
- **Model** and **Effort**: Codex's list comes from its app server on that machine; Claude offers Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.2 and Fable 5.1.
- **Attachments** (chats on this Mac only): drop or paste files and images, or use the paperclip (**Choose Files…**, **Paste File or Image**). Up to eight per message, each a regular file of at most 20 MB, never from credential folders such as `~/.ssh`, `~/.aws` or the Keychains folder, nor Codex's and Claude's own sign-in files. Codex receives images as images and other files as paths in the message; Claude receives every path in the message and reads the files itself. Pasted image data is first written, owner-only, to Burro's temporary folder.

While a chat is working, the composer offers instead:

- **Stop** (■, ⌘.): ends the running Codex turn (`turn/interrupt`) or stops a Claude background session (`claude stop`), on this Mac or another machine; the conversation is kept. A Claude chat running in the Claude app or a terminal can't be stopped from outside: the button reads **Stop it in Claude** and opens it there.
- **Queue for when it's done** (Return): holds your message and sends it once the chat has looked idle for a few seconds, through the same path and checks as a normal reply. One queued message per chat; it shows above the composer with **Edit** and **Cancel** until it goes. It is dropped with a notice (and its text kept, so you can edit it back) if the chat disappears for a minute, turns out to be open elsewhere, or is still busy a day later. A message is marked as sending before it goes, so one found marked after Burro quit mid-send is never sent again; you're told to check the chat instead. Queued messages are kept in `~/Library/Application Support/Burro/reply-queue.json` (owner-only).
- **Steer now** (Codex only): adds your message to the turn Codex is on now (`turn/steer`). If that turn has already ended, Burro says so; send it as a normal reply.

When a reply can't go, a single line replaces the pickers with the reason and, when there is one, the action that helps: **Open in Claude** (the chat is open in the Claude app or a terminal), **Attach in Terminal** (`claude attach` for a Claude background session on this Mac that can't take a reply now), **Attach on <Machine>** (the same over SSH, opened in Terminal), or why the machine can't take replies now.

Codex replies go through Codex's app-server daemon: Burro resumes the thread and starts a turn. On another machine the same happens over SSH, which needs Codex's standalone install there (the daemon only runs from it); Burro tells you if it's missing. Claude replies run `claude --bg --resume <id>`, which continues the conversation in the background under the same id. That only works when nothing has the session open, so Burro checks `claude agents` first:

- Nothing has it open (including background sessions that already finished): the reply goes straight away.
- Its **background session is still open but idle** (how `claude --bg`, and so every chat Burro starts, is left after its turn): **Send** (its help says so) stops that one session with `claude stop`, waits until `claude agents` no longer lists it as running (a few seconds at most), then resumes it with your message. This happens only for the chat you're replying to, only when it isn't working or asking anything, and only when no `claude attach` for it is running. If the stop fails or can't be confirmed, nothing is sent and the reason is shown. A queued message for such a chat goes the same way. On another machine the fixed `remote_reply.py` script does the same checks there.
- Open in the Claude app or a terminal, or a background session that is busy or waiting for an approval: Burro says so instead of starting a copy, and never stops it.

Approval prompts from a reply wait in the agent's own app (or `claude attach`) and show as **Needs you** in Burro. The live behaviour of stopping, steering, queuing and continuing against real Codex and Claude sessions, and on a real remote Mac, follows the providers' documented commands but hasn't been exercised end to end.

**Managing chats.** The **⋯** menu in a chat's header, and a row's context menu, have **Rename…** (a Codex chat is renamed in Codex; a Claude chat gets a title only Burro shows, with **Use Claude's Title** to go back), **Pin to Top** / **Unpin** (Burro only), **Mark as Read Here**, **Open in Codex/Claude**, and **Archive in Codex…** (asks first; it leaves Codex's list and Burro's, and Codex can unarchive it) or, for Claude, **Hide in Burro** (it comes back by itself when the chat has new activity). Titles, pins and hidden chats are kept in Burro's preferences.

**Seen here.** Opening a chat on this page (or **Mark as Read Here**) marks its result as seen in Burro: it stops counting as ready to read in the Chats list and badge, on Home and in the notch, until it has new activity. A chat counts as seen only while Burro is the active app with the Chats page in its focused window, and a seen mark never suppresses a notification or the Brief's triage for that chat. Only Burro's own copy changes; the providers' unread markers are never written, so the chat can still show as unread in Codex or Claude. Up to 2,000 seen marks are kept in Burro's preferences.

**Drafts.** When the Orchestrator has a reply drafted for a chat (from [triage](#the-brief) or because you asked), one line above the composer shows it: **Draft from the Orchestrator: …** with **Use**, which puts the whole draft in the composer for you to edit and send the usual way (it never sends, and takes the draft off the Brief), and **Discard**.

**Details panel.** The panel on the right (toggle it with the sidebar button; it shows when the window is wide enough) gives the folder and branch, machine, model and effort, how full the context is (a percentage when the provider records the model's window, as Codex does, otherwise tokens), lines changed since the branch left its base (a read-only `git diff --shortstat`, this Mac only) with uncommitted and unpushed counts, when it started, and subagents still running. For a worktree on this Mac, the Folder row offers **Open worktree** (the Worktrees page with it selected) and **Review cleanup…** (the usual cleanup confirmation).

Burro shows the latest 300 messages, read from at most the last 16 MiB of the chat's file; older ones say so at the top. On this Mac the Rust worker finds and parses the file in its own process (separate from history scans, with a 10-second deadline), keeping the parsed messages of the last eight chats it read in memory, never the raw file. A chat on another machine is read through Burro's local copy of its transcript (below); without that copy, a fixed read-only script (`remote_transcript.py`) fetches it in full over your SSH connection. Clicking a chat anywhere else in Burro (Home, Today, the dock, the ⌘K palette, a notification, and the notch and menu bar with **Open chats in Burro** on) opens it here.

**Chats on other machines.** The first time you open one, Burro copies the end of its transcript (the last 4 MiB, starting at a line) into its remote cache and shows it; the next time it opens at once from that copy and then catches up. A live remote chat fetches only the bytes added since the copy (a check that finds nothing new returns a header of about 120 bytes); a replaced or rewritten file starts the copy over. While the machine can't be reached, the copy stays readable with a line such as "As of 14:02 · Mac mini unreachable · retrying in 30 s" (or "no longer on Mac mini" when the transcript is gone there), and catches up as soon as monitoring reaches the machine again. When the copy doesn't start at the beginning, **Show earlier messages** at the top fetches more of its history (the copy never grows past 16 MiB that way) and shows up to 500 messages. The reading is done by the fixed read-only script `remote_tail.py`, which opens only that chat's transcript under `~/.claude/projects`, `~/.codex/sessions` or `~/.codex/archived_sessions` there. Where the copies live and how long they're kept: [Other laptops and servers](#other-laptops-and-servers).

### Orchestrator

The **Orchestrator** is one Claude Code chat that Burro runs for you, and keeps the [Brief](#the-brief) on Home. Open its page with **⌘2** or the sparkles icon in the top bar, or ask from the Brief's composer on Home: what needs you, where a project stands, what a chat on another machine did, or to draft a reply or a new chat. Return sends; ⌥Return adds a line; the stop button ends a turn. The **model** menu in its header picks the Claude model (Fable 5.2 by default; Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 too) and the **effort** menu how hard it thinks (Low to Max, High by default); both apply from your next message. Its big model runs only while it answers a message you sent; the automatic reading of chats behind the Brief is a separate, small model (below).

**One conversation a day.** The first question of a local day starts a fresh conversation, and later questions that day continue it, so its context never grows without bound. **New conversation** starts another one today. Earlier conversations (the last 30 days) are listed under **Earlier conversations** in the page's **⋯** menu; choosing one shows that conversation with a **Back to today** bar.

The page has three tabs:

- **Conversation**: one turn per question: your message, a one-line summary of what it checked (click to open the timeline of steps and their output; it stays open while it works), its answer, and under it any proposal cards and to-do changes. On the right, **Agents** shows your machines with running and waiting counts, the chats started from its proposals, then chats that need you, are working or are ready to read, each with its subagents underneath. Click an agent to read it in Chats, or hover and click the sparkles button to ask the orchestrator about it.
- **Memory**: standing notes it is given at the start of every answer, global ones first, then your main project's, each marked as yours or noted by it. Add a note (global or for a project), edit one in place or delete it. It adds its own with `remember` and drops them with `forget`. The list starts with one note, "End answers with a one-line TL;DR.", added once. It no longer reads your own Claude Code settings or CLAUDE.md files.
- **Runs**: how many model runs it made today and what they cost, then the latest runs with their trigger (a question you asked, a triage batch or the morning brief), model, time taken and tokens. Costs are what Claude Code reports at API prices; on a subscription the runs count toward your usage windows instead.

**Proposed replies and chats.** The orchestrator never sends a message or starts a chat itself. When it drafts a reply to a chat (on any machine) or a new chat (on this Mac, or on another machine in a folder Burro knows there), the draft appears as a card under its answer: one line saying what will happen ("… on devbox" for another machine), the full text to edit in place, and **Send** or **Discard**. A waiting card is outlined in amber (**Needs your OK**). Nothing goes out until you click **Send**: a reply goes through the same path as the Chats composer (keeping that chat's own access, model and effort, and continuing an idle Claude background session as Send does there), a new chat through the same launch as New chat (Ask before acting unless the proposal names another access level; on another machine the folder, Claude's trust and the install are checked there when you click). The card then shows Burro's confirmation, or the error, in which case it stays unsent. If the chat is no longer waiting for you the card says so and the button reads **Send anyway**; if Burro can't see the chat, or a new chat's folder is gone, it can't be sent. Proposals survive a relaunch and expire a day after they were made: an expired card can only be discarded, and any proposal leaves the file after a week. Replies triage drafted are listed under **Drafted by triage**, and proposals no visible turn shows (from an earlier conversation) under **Proposed earlier**.

**To-dos it changes.** `add_todo` and `complete_todo` don't wait for Send: Burro applies them to today's to-dos at once (added ones are marked as the Orchestrator's) and shows a line under the turn, "Added to-do … · Undo" or "Completed … · Undo". Undo is offered for a day; a change that couldn't be applied says why.

**How it runs.** Burro runs it with `claude -p` in `~/Library/Application Support/Burro/Orchestrator`, with no user or project settings (so no hooks, permission rules or CLAUDE.md) and only Burro's MCP server, not your other MCP servers. Claude Code's built-in tools are switched off except the loader for deferred tools, so it can't read or edit files itself, run commands, browse the web or start sub-agents; anything else is denied rather than asked. Its brief, today's date and its memory go in as an appended system prompt each turn. Its tools come from the bundled MCP server (`burro-mcp`), which reads a snapshot Burro writes before and during each turn:

- **brief**: the Brief's open items, with kinds, questions, drafted replies and age. Its instructions tell it to call this first and answer from it.
- **overview**: machines and agent versions, folders it can start chats in on other machines, the main project, projects, chats by status with their subagents (chats already in the Brief are only counted), and today's to-dos.
- **list_chats** (filter by status, machine, project or text), **chat_digest** (a chat in a few lines: triage's reading when there is one, its last ask and answer, the question it ends on and its worktree's state, without diffs) and **read_chat** (any chat on any machine, read the same way as the Chats page; it ends with a cursor, and `since` returns only what's new after it).
- **list_worktrees**, **read_shipped** (Burro's cached Shipped summaries; it never runs `gh`), **usage** (what's left of each Claude, Codex and Grok window and when it resets).
- **read_notes**: your notes, only when **Let it read my notes** is on in the page's **⋯** menu (off by default).
- **read_file** and **search_files**: text files in your git repositories and their worktrees on this Mac, nothing else (a chat's working folder that isn't a repository is not readable). All of `~/Library` and every hidden file or folder directly in your home folder (`~/.config`, `~/.netrc`, shell history and the like) are always off-limits. A file is readable only when the path actually opened (checked on the open file, so links and `..` can't get around it) lies inside a repository or worktree folder from Burro's snapshot and outside Burro's own data (`~/Library/Application Support/Burro`, which holds tracked activity, notes and its own files, and `~/Library/Caches/Burro`), `~/.claude`, `~/.codex`, `~/.ssh`, `~/.gnupg`, `~/.aws` and the Keychains folder. Files shaped like secrets (`.env`, private keys) and git internals are refused, the home folder itself is never a root, reads are capped and searches skip build and dependency folders.
- **reply_chat** and **start_chat** (with an optional `machine`): record a proposal; nothing is sent.
- **add_todo** and **complete_todo**: record a to-do change that Burro applies at once with Undo.
- **remember** and **forget**: edit its memory.

Its folder holds `state.json` (the snapshot: chat titles, paths, machine names, worktree facts, to-dos, cached Shipped summaries and usage windows, your notes only when allowed; no message bodies, credentials or tracked activity), `actions.json` (proposals and to-do changes), `brief.json` (the Brief), `memory.json`, `runs.jsonl` (one line per run, kept 30 days and at most 2 MB), `mcp.json` (the tool server's configuration) and the `Triage` folder triage runs in. All are owner-only; files both Burro and `burro-mcp` write are changed under a lock. A short turn takes about 5–15 seconds and is billed to your Claude account like any Claude Code chat.

### The Brief

Home's Orchestrator card is the **Brief**: what your chats need, kept current between questions. Its sections, each hidden when empty:

- **Needs you** (amber): the chat's title, the question it ends on in one line and, when that chat has a draft (triage's, or a reply the Orchestrator proposed), the reply inline with **Send**, **Edit** and **Discard**. Send uses the proposal card's own path; Edit opens the text in place. Click the row to open the chat. Unlike the attention strip above it, it also catches chats that ended a turn on a question.
- **Finished**: a one-line outcome per chat.
- **Stuck**: chats that have been working with no sign of life: no new output for 45 minutes, or three hours while one tool call is still running or when only a status time can be seen (a Claude chat on another machine). This needs no model call.
- **Shipped**: one line from the cached Shipped summary.

Right-click an item to **Dismiss** it. An item resolves on its own when its chat moves on (works again, shows new activity, or stops waiting with nothing left to read); a newer reading replaces it, and items leave after seven days. Under the sections, the composer stays collapsed to one line (**Ask the Orchestrator…**); an earlier answer only shows as a link with its age. The footer reads "Triage: 9 today · On", "· Off", or why it's paused, and turns automatic triage on or off.

**Triage.** When one of your chats starts waiting on you or finishes a turn (on any machine; subagents excluded), Burro queues it. A batch goes 30–45 seconds after the first chat (sooner once five are waiting) as one `claude -p` call to Claude Haiku 5.5 through your signed-in Claude Code CLI, at low effort, with no tools, MCP servers, settings, hooks, CLAUDE.md or saved session, run in the Orchestrator's `Triage` folder (so it never shows as a chat). One call at a time, at most five chats each. For each chat it is sent only the title, project and machine, the last message you wrote (up to 2,000 characters), the last assistant message (up to 4,000), the last five tool lines and the Orchestrator's memory notes for that project, all marked as data; nothing from activity tracking, and any path into Burro's Activity folder is blanked. The end of each transcript is read on this Mac or over SSH as Chats does, and a chat whose last messages were already triaged is skipped. It answers whether you're needed (a decision, a blocker, a failure, a loop) or the chat is done, with a headline and, when a short reply would unblock it and it is confident enough, a drafted reply in your voice. A draft is only ever a proposal in `actions.json`: you Send, Edit or Discard it on the Brief, take it into the composer with **Use** in Chats, or ignore it. Drafts also show in the menu bar (**N drafts ready**).

Limits: automatic triage is on by default and runs at most 150 times a local day (**Daily cap** 25, 50, 100 or 150 in Settings) and 30 times an hour, and pauses itself while Claude's session window has under 15% left or its weekly window under 10% (when Burro knows them). The **morning brief** (on by default) triages chats still waiting on you or unread from the last day, up to five, once a day on the first activation after 5 am. Every triage run is logged in `runs.jsonl` with the Orchestrator's own runs, so the footer and the Runs tab agree, and counts toward your Claude usage. Triage against real chats and real Haiku runs, and the banner updates, are implemented as described but haven't been exercised end to end.

**Settings → Orchestrator** has **Triage chats automatically** (the same switch as the footer), **Daily cap**, **Morning brief**, a plain description of when it runs and pauses, and today's count.

On today, until something ships, the day is one quiet "Nothing reached GitHub yet today" line with that recap under it. Click the day-before recap to show that day on the page, or a week to open the Timeline. Click any row to open it on GitHub, the repository name to open the repository, and **Copy** to copy the day as plain text for a chat or standup. ### Activity tracking

Burro can track where your time goes, entirely on this Mac. It is **off** until you press **Turn on** on the Today page's **Activity** card. It records only while Burro is open, so turn on **Settings → Startup → Open at login** (or **Open Burro at login** in the Activity **⋯** menu) to have it start with your Mac, quietly and without the window; the switch shows macOS's own login-item status, and if macOS asks for approval, **Open Login Items…** takes you to System Settings › General › Login Items. It records only the frontmost app, its window title and, in Safari, Chrome, Arc, Brave, Edge and Firefox, the site's host (`dashboard.stripe.com`, never the path or query). Arc keeps its accessibility tree empty until an app asks for it, so when Arc (or Chrome, Brave or Edge without a readable address field) comes to the front, Burro asks it once per launch to build that tree (`AXManualAccessibility`) and then reads only the page address of the window's web area, keeping the host. Building the tree costs the browser some CPU and memory while it runs; Burro reads no more often than before. To turn this off, switch off **Settings → Activity → Read the site in Arc and Chromium browsers** (it applies at once; those browsers then fall back to window titles). No screenshots, no text recognition, no AI, no keystrokes, and nothing is sent anywhere.

- **The day view**: once tracking is on, the Today page shows the day under the summary. A **timeline** has one block per stretch of activity: tinted by category, with the app's icon, a one-line title and its time range. It starts at the hour of the day's first block and ends at the last block (or now); an idle gap longer than 45 minutes is a thin **Idle · 2h 10m** divider instead of empty space (hover for its range), and shorter gaps keep their length. **Idle** means Burro was recording and you were away (no input; sleep and a locked screen count as away too). A stretch of 5 minutes or more when Burro wasn't recording at all (closed, paused or turned off) is a separate, fainter **Not recording · 2h 10m** divider wherever it falls, before the first block, between blocks or after the last; a day that opens with one starts at 0:00. Days from before Burro kept this record, and imported days, show no Not recording dividers. Time in one category with gaps under 5 minutes is one block; three or more short turns in a row (each under 10 minutes, such as Claude, Arc, Claude, Arc) are one **Switching between Claude and Arc** block; anything under 5 minutes folds into its longer neighbour (Private time never folds either way); blocks with under a minute of time aren't drawn (their time still counts). A block is titled by its main app (over 60% of its time) and that app's most-seen site or window title, such as "Xcode · ActivityLog.swift" or "Arc · github.com", never repeating the app ("Claude", not "Claude · Claude"; a trailing " - Slack" naming the app is dropped). Private blocks say only "Private" and the app. Titles come only from the app names, cleaned titles and hosts already recorded (no AI). Short blocks get a minimum height and the hour lines stretch with them; on wide windows the hours stretch further so the timeline fills the card beside it. Today opens at "now". Beside the timeline at a matching height (below it on narrow windows; on a short day whose timeline would leave it mostly empty, the timeline keeps its own height and this card is one row beneath it): **Your day so far**, with a donut of categories and the total, the apps and sites with the most time (only those with a minute or more), the day's focus stretches on a strip (a stretch is non-Break time that idle time or a break under 2 minutes doesn't end; the longest is highlighted) and what Break went to. The lock screen, login window, screen saver and system password prompts aren't activity: Burro records nothing while one is in front, and drops any such time already stored. The day arrows work for past days.
- **Home**: while tracking is on, Home shows a **Today so far** card under the to-dos: focused and tracked time, a category bar, what you're on now (the app, and its site or title unless it's private), Break time and the longest focus stretch. Click it to open Today. It reads today's file when Home appears and then once a minute while Home is on screen; with tracking off it isn't shown.
- **Window titles and sites** need macOS's Accessibility permission. Without it Burro still counts time per app, and the card shows **Allow…**, which asks macOS once and opens System Settings → Privacy & Security → Accessibility. Burro only asks when you click.
- **Pause** stops recording until you press **Resume** (it stays paused after a restart). The **⋯** menu also has **Turn off**, **Away after** (2, 5 or 10 minutes without input before you count as away; 2 by default, applied at once), **Open Burro at login**, **Delete this day…** and **Delete everything…** (each asks first; delete everything keeps your category rules).
- **Privacy rules**, applied before anything is stored: password managers and credential apps (1Password, Bitwarden, Dashlane, LastPass, KeePassXC, Keychain Access, Passwords, System Settings and similar) count as **Private** time with no title. Private and incognito windows (recognised by their window title or toolbar label) keep no title or site. Banking and payment sites (a built-in list such as boursobank.com, boursorama.com and paypal.com, any host with a bank word in it, plus sites you mark) keep no title and show as **Private**. Every title is cut to 120 characters, and email addresses, IBANs and runs of six or more digits (card numbers, account numbers, codes; spaces and dashes between them allowed) are replaced by `[email]` and `[number]`. Web addresses in a title lose everything from `?` or `#` on, and long runs of mixed letters and digits (24 or more characters, such as API keys) become `[token]`.
- **Categories** are simple rules: Build, Agents, Design, Analytics, Comms, Docs, Browsing, Break, Private and Other. The first match wins: Private, a site rule of yours, a built-in site, an app rule of yours, a built-in app, a word in the title, any other web page (Browsing), then Other. Site rules cover subdomains. Right-click a timeline block or an app or site row to change its category (it applies to past days too) or to **Treat it as private**, which also rewrites the days already stored.
- **Cost**: it reacts to app switches and window changes rather than polling. A check every 30 seconds notices when you've been without input for the **Away after** time (two minutes unless you pick 5 or 10), and idle time starts at your last input. While recording, a 30-second heartbeat (and waking or unlocking) extends the day's record of when Burro was recording. Only your own input (keys, clicks, scrolling, moving the mouse) ends idle time: apps an agent brings to the front while you're away aren't counted. While you're away the check runs every 5 seconds, so your return is noticed quickly. Sleep, screen lock and switching users stop it. A window that renames itself constantly is read at most every five seconds, flicks under five seconds fold into their neighbours, and the file is written at most every 30 seconds.
- **Storage**: `~/Library/Application Support/Burro/Activity/` (owner-only), one `YYYY-MM-DD.jsonl` file per day (at most 4 MB) with start, end, app, bundle id and the cleaned title and host, and beside it a `YYYY-MM-DD.coverage` file (owner-only, at most 64 KB) holding only the start and end times of when Burro was recording that day: from when recording starts (tracking on, not paused, Burro open) to when it stops (pause, turn off, quit), so a crash loses at most the last 30 seconds. Deleting a day or everything deletes its coverage file too. Days older than 365 days are deleted at launch and once a day. Your rules are in `rules.json` in the same folder. Activity never goes into the orchestrator's snapshot, `burro-mcp` (its file tools refuse Burro's data folder), triage's input, remote machines or logs.
- **Importing Dayflow history** (one time): `burro-inspect --activity-import-dayflow --dry-run` reads `~/Library/Application Support/Dayflow/chunks.sqlite` read-only and prints what it would write; drop `--dry-run` to write it (`--database <path>` and `--activity-dir <path>` point it elsewhere). Each Dayflow card becomes one timeline block with its own title (scrubbed like window titles) and category: Engineering / Product → Build, Distraction → Break, Data & Insights → Analytics, Research & Strategy → Docs, Communication → Comms, System and anything else → Other; Idle and deleted cards are skipped; Personal cards, banking or private sites, password managers and titles mentioning a bank or a private window become Private with no title. Your own site and app rules still win over an imported category. A day that already has tracked time keeps it, and imported time on that day stops where tracking began. Running it again replaces what it imported before, and it prints only counts and hours, never titles, sites or apps.

### New chat

**⌘N**, **New chat** in the top bar or on the main project card, the dock's **+**, or **New chat…** in the ⌘K palette opens the New chat sheet. It is one large prompt field with the cursor in it ("What should Claude do in burro?") and, under it, one line of chips: **project ▾ · agent model effort ▾ · access ▾ · machine ▾**. They start filled from the last launch in that project: each project remembers the agent, the model and effort you used with each agent there, and the access of its last launch; a project without a memory takes the agent's last values, then the defaults (Codex with its default model and Ask before acting; Claude on Opus 5.5). Switching project brings back its choices, switching agent brings back the model and effort last used with it, and a model or effort no longer offered falls back to the default. The project chip lists recently used projects first (**Choose folder…** for another), and **⌘1–⌘9** pick them. The agent chip picks **Codex** or **Claude Code** with its model and effort (Codex's list comes from its app server on that machine; Claude offers Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.2 and Fable 5.1). The access levels:

- **Ask before acting**: edits inside the workspace and asks before anything else (Codex `workspace-write` + `on-request`; Claude `manual`). Waiting chats appear at the top of Home and in the notch.
- **Edit files freely**: no approval prompts; Codex keeps its workspace sandbox (`never` approval), Claude uses `acceptEdits`.
- **Read only**: reads and plans, changes nothing (Codex `read-only`; Claude `plan`).

**⌘↩** (**Start chat**) starts the chat and follows it on the Chats page; **⇧⌘↩** starts it and stays on the current page; Escape cancels. Starting closes the sheet at once: the chat shows in a **Starting** group at the top of Chats ("Starting… checking it got going" while Claude's start check runs, which can take up to 20 seconds) and turns into the real chat as soon as Burro's feed lists it. If it fails, the row shows the reason with **Retry** (the sheet again, prefilled with the same request) and **Dismiss**. A chat that started but isn't listed after 45 seconds (90 on another machine) says so and offers its provider's own view instead of spinning.

You can also open the sheet prefilled, from **Start chat: "…"** in ⌘K (the typed text becomes the prompt), **Start chat from this…** in the context menu of a to-do or a note (on Home or in the Notes window; a to-do that names a project Burro knows starts there), **New chat here** on a worktree, or Retry. These only fill in the sheet; Start is the only thing that launches.

Codex chats start on Codex's shared app-server daemon (Burro starts it if needed), so they keep running after the sheet closes and open in the Codex app. Claude chats start as `claude --bg` background sessions; **Attach in Terminal** opens `claude attach <id>`, and `claude agents` lists them. A Claude start counts only once its transcript exists. Claude only starts in folders you've already trusted in Claude Code; run `claude` there once if Burro says it isn't trusted. Burro never marks a folder trusted for you.

**On another machine.** The machine chip lists **This Mac**, then every machine you added with its status line ("Studio · Connected · checked 12 s ago"). A paused machine, one with an invalid address and one that is currently unreachable are listed but can't be picked, with the reason; one not checked yet can (the start itself will tell). Each machine remembers its own recent projects, and switching machine brings back its last one; the same path on two machines is two projects. With another machine chosen, the project chip lists that machine's folders: the remembered list at once, then a fresh one over SSH (a spinner in the chip; a failure is shown and the remembered list kept). The list comes from the fixed read-only script `remote_folders.py`: Claude's projects in `~/.claude.json` with its trust flag, working folders from Codex's newest state database and from Claude sessions of the last 30 days, at most 300, each with its repository and branch (read from files; it runs no program) and, for a Claude chat, a quiet "not trusted by Claude yet". **Type a path…** checks a folder on that machine (a real directory you own after resolving links) and says exactly why when it isn't usable. Codex models come from that machine (remembered; "Default" while loading). Folder lists and models are remembered in Burro's remote cache.

Starting there goes over SSH with remote monitoring's strict options, the request sent as base64 to a fixed script, so no folder, prompt or name reaches a remote shell. Codex: after the folder checks out, the same `thread/start` and `turn/start` as on this Mac through `codex app-server proxy` there, which needs Codex's standalone install on that machine. Claude: `remote_launch.py` checks that Claude Code is installed and the folder is trusted (read-only), starts `claude --bg` through your login shell detached from the SSH connection, and collects for up to 20 seconds what the local start check reads; a session that stopped at a prompt, ended, or never wrote a transcript is stopped and removed there (only the one this start created). As soon as the machine answers, the chat is put in that machine's list and opened on the Chats page, so its conversation loads before the next check lists it; that machine is checked right away. A failure says exactly why, with Retry: unreachable (with when it was last seen), Claude Code or Codex not installed, not Codex's standalone install, folder not trusted by Claude (run `claude` in that folder there once and accept), blocked at a prompt, or no transcript within 20 seconds. If the SSH call timed out after asking, the row says the chat may have started anyway and will appear at the next check if it did. The ⌘K palette's **New chat on <Machine>…** and **New chat in <folder> on <Machine>…** open the sheet with that machine (and folder) chosen. Starting chats on a real remote Mac is implemented this way but hasn't been tried end to end.

  Claude Code can reset that grant when renewing its login, even after **Always Allow**. Checked with Claude Code 2.1.283.

Ambiguous, unsupported, revoked, or unavailable accounts show explicit states. Browser cookies and reset-credit redemption are not implemented. Proto3 zero usage is accepted only when the complete response proves an active current period; missing or malformed data stays unavailable.

**Usage settings** controls provider enablement, one/five/fifteen-minute refresh, remaining versus used display, pace/model rows, and local history. Manual refresh has a 15-second cooldown and respects provider rate-limit backoff. Temporary network failures retry automatically after 30 seconds, increasing up to five minutes; expired Claude credentials are rechecked every minute. After wake, session activation, or reopening Burro, transient failures receive a debounced silent retry; locked Keychains retry every 30 seconds and do not show a Connect button. Healthy providers keep the selected cadence, and wake events never bypass provider rate-limit backoff. Timeouts, rate limits, and pending renewal do not offer a misleading sign-in action. Providers publish as each request completes; a slow account never hides another provider’s available reading. Providers fail independently. A failed fetch clears that provider's old values; disabling Usage or changing profiles invalidates in-flight results. Missing percentages and resets stay unknown; expired reset dates never fabricate a refill. Readings older than ten minutes are stale. When connecting Claude for the first time, choose **Always Allow** in the native Keychain prompt if you want future approved reads to be silent. A locked Keychain waits for unlock; a revoked provider session or organization policy can still require user action.

### Done and unread status

Burro reads the provider apps' saved unread markers on this Mac. A successful Codex completion event, or an idle Claude desktop session with completed turns, must also be present. Codex internal sub-agent/guardian runs never produce Done notifications, even if they retain unread markers. Live workers still appear as working or needing input. Codex rows prefer the app's saved display name over the original prompt. Working, scheduled, needs-input, unknown, and stale-remote states take precedence. Clicking a row opens the provider; Burro waits for its saved read marker to clear on the next local refresh. It does not mark chats read itself or use a recent-completion timer. Done is separate from worktree safety: an open idle process still keeps its worktree in use.

Codex stores read state per account and execution host in `.codex-global-state.json`. Burro selects the account from the newest thread with creator identity metadata (or the sole saved account on older installations), never unions account histories, and ignores legacy migration snapshots. Switching accounts without creating an attributed thread can leave that selection behind; missing/ambiguous schemas show a visibility warning. The unread-status reader does not access authentication files or tokens.

Claude's `epitaxy-unread-v1` preference is read from its Chromium Local Storage, including manually unread IDs. The reader follows the current LevelDB manifest, sequence numbers and deletion markers, validates checksums, and reads only the relevant indexed blocks. It does not open or lock the provider database. Records in the live log are read the way LevelDB writes them, including ones that start right at the edge of a 32 KiB block, and the unfinished end of a log being appended is ignored rather than treated as damage. Missing registry/session metadata can prevent a Done badge; unsupported or changing storage fails closed and is retried on the next refresh. The result, or a failure, is reused while every database file keeps the same size, identity and modification time, so an unchanged store is parsed once; Codex's unread list is likewise reused while `.codex-global-state.json` and its `state_*.sqlite` files (with their WAL) are unchanged. A read-state failure shows as a notice but doesn't keep agent checks on the 3-second cadence. The format reader follows [LevelDB tables](https://github.com/google/leveldb/blob/main/doc/table_format.md) and [logs](https://github.com/google/leveldb/blob/main/doc/log_format.md).

Remote SQLite reads can use a stable, journal-free checkpoint when read-only WAL access is unavailable; a changed checkpoint or live journal cancels that fallback. Remote hosts return completion metadata; this Mac applies its own unread list using Codex thread UUIDs and Claude bridge IDs. Local unread IDs are never sent over SSH. Remote Codex completion history shares the existing 2,000-row/inspection-time limits; unread results beyond that coverage may be missing. Another laptop's `local_` Claude ID is never treated as a local read marker. Offline results become Last seen, not Done.

## Mac Health

**Mac Health** (this Mac's card on Home, the top bar, **⌘8**, or the notch **Mac** tab) shows CPU use and load, memory used and pressure, swap, startup-disk space, thermal state, and your busiest processes. It samples only while one of those views is on screen: system counters every five seconds, the process list every 15 seconds, and disk space every minute. A covered, minimized or hidden window, or a sleeping display, pauses it.

**Left running** lists things that usually outlived the work that started them:

- **Still busy:** a process outside any app still using at least 25% of a core after an hour of CPU time.
- **Long-running watcher:** a test runner, bundler, or `tail -f` running for over two hours. Jest and Metro worker pools count toward whatever started them; they are listed alone only after that parent exits. Memory figures are physical footprint, the same measure as Activity Monitor.
- **Idle server:** a process listening on a port with no open connections for over 12 hours.
- **Agent script:** a script started from a coding agent's temporary folder over six hours ago.
- **Orphaned:** a process outside any app whose parent exited at least an hour ago.
- **Headless simulator:** a booted iOS simulator with no Simulator window open for over 30 minutes.

Apps, macOS services, common background tools (watchman, syncthing, ssh-agent and similar), open Claude/Codex sessions, and helpers an app or agent started directly are never listed. **Stop…** asks first, then sends a normal quit request only if the process still has the same start time and executable; if it ignores that, the action becomes **Force Quit…**. **Shut Down…** runs `xcrun simctl shutdown` for that simulator. **Ignore** hides that tool in that folder until you choose **Show ignored**. The notch tab only shows a summary; actions stay in the desktop page.

### Keep awake

The **Keep awake** card at the top of Mac Health (also in the menu bar's **Keep Awake** submenu and **Settings → Keep awake**) keeps this Mac from sleeping:

- **Keep awake → For 1 hour / 2 hours / 4 hours / Until I stop.** **Stop** ends it; **Change** picks another duration without asking again.
- **While agents work on this Mac.** Stays awake whenever a Codex or Claude chat on this Mac is working (the Orchestrator included), then for the time you pick (**Stop**, 5, 15 or 30 minutes) in case another turn starts. Chats on other machines don't count.

An open lid stays awake through an idle-sleep assertion Burro holds, with no password; it ends the moment Burro does. A closed lid needs `pmset -a disablesleep 1` (the same flag as [NoSleepBar](https://github.com/EdgarHnd/nosleep)):

- **Allow…** (or **Settings → Allow Without a Password…**) asks for your administrator password once and installs `/etc/sudoers.d/burro-keep-awake`, allowing exactly `/usr/bin/pmset -a disablesleep 0` and `… 1` without a password, checked with `visudo` first. With it, both modes cover a closed lid and start and stop on their own. **Remove Permission…** deletes the file (not while a lid-closed session is on). A rule you installed with NoSleepBar works too.
- Without it, picking a duration shows the administrator prompt; cancel it and only an open lid is covered (**Include closed lid…** asks again). **While agents work** never prompts on its own, so without the permission it covers an open lid only.

Each lid-closed session runs a small shell watchdog that turns sleep back on when you stop or the request ends, when the agents are done, 30 seconds after Burro quits or crashes (a relaunched Burro, such as after a rebuild, takes the session over instead), when Burro hasn't checked in for 15 minutes, or on battery at 10% or less (plugging in resumes it). The **Lid closed** tag and the green dot on the top bar's Mac Health icon show a session is on; the notch **Mac** tab shows a line while the Mac is kept awake.

If sleep is turned off with no Burro session (left by a session whose watchdog was killed, or set by another tool or a `pmset` command), the card says so with **Turn sleep back on**. Burro turns its own leftover back on by itself when it has the permission; it never changes a setting another tool made unless you click.

## Other laptops and servers

Open **Remote sessions → Add remote machine**, or add a machine in Settings. Give it a name and the SSH address/alias you already use, such as `user@laptop.local` or `devbox`. Confirm that `ssh` connects from this Mac first. The remote machine needs macOS or Linux, Python 3, and readable Codex / Claude Code session metadata in the remote user's home directory.

- Both providers appear in the same notch feed, labeled with the remote machine and workspace. Clicking a remote agent opens it on Burro's Chats page; with ⌥ (or **Open chats in Burro** off) it opens in the provider app on this Mac when a usable link is available. Codex needs that host/thread in its connected-host catalog; Claude needs its existing remote session bridge. A Claude desktop session ID from another machine is never treated as local. Right-click → **Show in Burro** opens remote details. Local Finder/Terminal actions and local cleanup assessments never apply to remote paths.

Each machine is checked 10 seconds after its previous check while the Burro window is on screen, the notch is open, or a chat on a remote machine is working or waiting on you; otherwise once a minute. A machine that fails is retried after 15, 30, 60, then 120 seconds (never sooner than that cadence) until a check succeeds; **Refresh**, or adding or editing the machine, checks it straight away and clears the backoff. Slow or unavailable machines do not block local monitoring.
- A failed connection preserves the last observed sessions as **Last seen**, changes their state to unknown, and removes them from working/waiting totals. A sample that isn't renewed within 90 seconds (the one-minute cadence plus a probe's timeout) also becomes stale.
- Burro remembers each machine between launches. After every successful check that changed something (and at least every ten minutes otherwise) it saves the machine's chats and warnings, its OS and tool versions, the folders a chat can start in there and its Codex models. After a relaunch with that machine asleep, its chats show at once as **Last seen** (never as live, and never counted as working or waiting) and the Machines page shows its facts, until the first check replaces them. A chat just started there is shown from a placeholder kept in memory until a check lists it; placeholders are never saved.
- Each machine has a status line, in **Settings → Remote laptops & servers** and on its Machines card: "Connected · checked 12 s ago", "Unreachable since 14:02 · retrying in 30 s", "Last seen 14:02 · connecting…" after a relaunch, or "Paused", plus what Tailscale says about an unreachable machine when Burro has its peer list.
- All of Burro's SSH calls to one machine (session checks, chat transcripts, replies, media, machine and harness checks) share one OpenSSH connection (`ControlMaster`). Burro's control sockets live in `~/Library/Caches/burro-ssh` (or `/tmp/burro-ssh-<your uid>` if that path is too long for a socket), a folder only you can open and in which only Burro creates connections, so each shared connection was opened with Burro's strict options. A connection closes 2 minutes after its last use; each call keeps its own timeout. If that folder can't be prepared, each call connects on its own as before. Pausing a host removes its sessions from the feed. Removing or editing a host cannot reintroduce responses from its old connection.
- OpenSSH uses your existing authentication, SSH configuration, and verified host keys. It runs noninteractively with agent/port forwarding disabled. Burro does not accept unknown host keys, install a helper, copy provider credentials, change provider settings (it never marks a folder trusted for Claude), or open a listener on either machine. Every call sends one of Burro's fixed bundled Python scripts over standard input with its request as a base64 line: the session probe (metadata only); the transcript readers, when you open a chat and when [triage](#the-brief) reads the end of one that stopped; the media reader and the folder lister; and the reply, stop and launch scripts. A reply, a stop or a new chat runs there only when you click Send, Stop or Start.
- Codex and Claude's app-to-app pairings do not automatically authorize Burro. This version uses its own SSH connection; provider relay pairings and cloud-hosted tasks are not imported.
- An idle Claude parent, locally or over SSH, remains Running while verified child processes own its session-scoped background task output descriptors, or its subagent logs contain fresh unfinished lifecycle events. Ordinary helper processes and completed workers do not count. Long-running background commands (including servers) remain active until their processes exit. A task waiting in an explicit `sleep` delay shows **Scheduled** with a teal clock, stays in the active list, and does not count as Running or Needs you. This requires a session-owned task branch containing only sleep processes and waiting shell wrappers. Mixed tasks or active workers stay Running; ordinary OS sleeping/idle processes do not imply a schedule. After the delay, the next sample reflects the resumed command or completion. Burro does not infer a wake-up time or import provider scheduling systems. Worker progress expires to Unknown after two minutes without a terminal event; it is never treated as Done merely because the parent is idle. Claude workers can finish with an assistant stop reason or a SubagentHandback tool result marked `toolEndsTurn: true`. Both are recognized locally and remotely, so old completed workers do not keep an idle parent at Unknown. Live background commands and later resumed worker activity still take precedence. Waiting-for-permission status still takes priority. Worker logs predating the parent process incarnation are excluded. These checks inspect event envelopes and descriptor names, never task output or prompt bodies.
- Remote monitoring covers sessions, not remote worktree cleanup assessments. Codex writer locks/turn events and Claude process-start identity use the same conservative rules as local monitoring. Unsupported metadata appears as a visibility notice. Output, record counts, probe duration, and SSH runtime are bounded.
- Remote host names, addresses, optional ports, and enable flags are saved in Burro preferences. No passwords, keys or tokens are stored by Burro.

**What Burro keeps from other machines.** Everything lives in a private cache, `~/Library/Caches/Burro/Remote/<machine id>/`: folders only you can open (0700), files only you can read (0600), nothing read or written through a link, and excluded from Time Machine backups. Per machine:

- `host.json`: the last successful check's chats (titles, folders, states) and warnings, the machine's facts, the folders a chat can start in there and its Codex models. A `host.json` written for another address is discarded.
- Images and videos from chats you opened, with an index of each copy's remote size and modification time: shown again, a copy is checked against the remote file and fetched again only if it changed; with the machine unreachable, the last copy is shown. Images up to about 8 MB are fetched on their own, larger ones (up to 40 MB) and videos (up to 300 MB) when you click. Up to 1 GB in total across machines, and 30 days since last opened.
- Transcript copies of the chats you opened there: raw bytes of the end of each transcript, plus where that slice sits in the remote file, so the chat opens at once, stays readable while the machine is asleep and fetches only new bytes (see [Chats](#chats)). Up to 512 MB in total across machines and 30 days since last opened; a chat open on screen is never removed. They're tidied at launch and then hourly. Only the app writes them; the Orchestrator's `read_chat` always fetches remote chats in full and never reads this folder.

Older copies are removed by when they were last opened. ## What the labels mean

Activity and cleanup answer different questions: **Inactive** means no observed live use; **Ready to remove** means Burro can preserve the folder in Trash while keeping its commits on a verified local branch.

| Cleanup status | Meaning and next step |
| --- | --- |
| **Ready to remove** | Clean tracked/untracked checkout, no attached live/idle/uncertain chats or processes, successful visibility checks, and a local branch contains HEAD. Moving the folder to Trash keeps that branch. |
| **Local changes** | Modified, staged, or untracked files need saving or discarding. The inspector and blocker sheet show filenames. |
| **In use** | Close the attached chats or processes before removing the checkout. |
| **Protected** | Primary checkout, protected branch, user protection, Git lock, pinned chat, or another registered worktree nested inside. |
| **Archive in Codex** | Use the chat's archive action for Codex-managed worktrees; Burro does not unregister them. |
| **Save commits first** | Detached HEAD has no verified local branch containing it. Create a local branch at HEAD first. A remote-tracking ref alone is insufficient. |
| **Git in progress** | Finish the Git operation or resolve its lock. |
| **Cannot verify** | Missing registration/folder, submodules, incomplete provider visibility, or failed Git inspection. Investigate the specific reason shown. |

These are point-in-time observations; processes can start after a scan. Unknown evidence never becomes ready. Ignored files (including environments and dependencies) do not prevent recoverable removal because the entire folder moves to Trash.

## Cleanup and recovery

Open **Cleanup** to see inactive linked worktrees, with ready folders first. **Ready to remove** filters only eligible checkouts; the sidebar, table, inspector and confirmation use the same readiness decision. The table names the checkout folder and labels its branch explicitly. Header totals apply to the visible worktrees. Use **Select ready** to select eligible rows within the current search and filter, or Command/Shift-click to build a selection. Clear deselects the rows. The multi-selection inspector summarizes ready and blocked items. **Move N to Trash…**, Command-Delete, Delete, and the context menu all open the same batch confirmation.

**Code & commits** separately shows integration evidence and the local branch preserving HEAD. Inclusion in locally available `origin/main`, `origin/staging`, `origin/master`, `origin/develop`, or your selected comparison branch is recognized even when the selected base differs. A small, clean, non-merge history may also be recognized as equivalent patches, including a combined squash. Squash candidates are shortlisted by commit subjects and accepted only when stable patch IDs match. Complex histories, changed titles without a match, timeouts, or output limits remain **Integration not confirmed**; this is not a claim that the PR is open. Burro does not query GitHub or fetch refs automatically.

Use **Compare with** to choose the repository's integration branch. This affects integration context, not whether commits are preserved. **An unmerged or unpushed branch can keep its commits after its checkout is removed.** Burro never deletes that branch. Uncommitted changes, activity, protection, and uncertain inspection still block removal. The older conservative `assessment` in CLI JSON remains an advisory merge/publication assessment; desktop cleanup uses the explicit retention evidence in `facts` instead.

Choose **Move to Trash…** for an eligible checkout or **Show blockers…** for the exact reason a checkout is unavailable. One short confirmation lists every selected folder, its retained branch, and any blockers. Only eligible rows are queued; blocked or changed rows are skipped. Codex-managed paths or attachments must be archived from their chats in Codex instead, even if local changes are the first blocker shown.

Confirmation triggers a fresh scan, verifies the same registration/HEAD/branch, rechecks Git and activity, and verifies the retaining branch still contains HEAD. It then moves the **entire folder** to macOS Trash. Ignored files and symlinks stay in Trash; external symlink targets are untouched. The retaining branch is rechecked before removing only that missing-folder registration, without force or global pruning. Trash must be supported for the folder's volume. If registration cleanup fails or evidence changes after the move, the error gives the preserved location and leaves the registration for manual inspection. No automatic removal occurs. Confirmed batches execute one worktree at a time through these same checks.

After confirmation, queued rows and counts update immediately and the sheet closes. A nonmodal progress strip lets you keep browsing, stop work that has not started, or inspect details. The current filesystem operation completes even after **Stop remaining**. Failed and skipped rows return immediately; a pre-cleanup background scan cannot resurrect pending rows or overwrite the later result. Successful rows remain hidden until a fresh post-batch scan reconciles the list. The result strip retains per-item errors, Trash destinations, kept branch and full commit, and a **Show in Finder** action; there is no success alert to dismiss. Results live in memory until dismissed or replaced by the next batch. A failure after moving the folder reports its preserved Trash location rather than claiming it stayed at its original path.

To restore, create a new worktree on the retained branch (or at the full commit shown for a detached checkout), then copy needed local/ignored files from Trash into it. The `.git` pointer in the trashed folder references the removed registration; dragging it back alone does not repair that registration. Files occupy disk space until Trash is emptied. Emptying Trash is permanent. Fresh checks reduce but cannot eliminate races with other processes.

## Agent detection and limits

- **Codex:** opens the newest `~/.codex/state_*.sqlite` read-only; joins chat workspaces and worktree attachments; inspects existing writer locks without creating them; reads bounded 512 KB transcript tails for turn-start/completion events. Held writer locks plus events distinguish working from open/idle. Recent unfinished events without a lock are marked recent activity, not confirmed running. Missing/unsupported schemas produce a visible notice and prevent cleanup readiness.
- **Claude Code:** reads `~/.claude/sessions/*.json`, verifies the live executable, PID, and process start time, then uses its reported status plus bounded delegated-work checks for idle parents. Dead PIDs are inactive; uncertain or reused identities stay unknown. Unrecognized live status is unknown and protects the worktree.
- **Processes:** uses macOS libproc for same-user process working directories, including terminals and dev servers. The scanner and its descendants are excluded. A nested worktree owns its own activity instead of incorrectly attributing it to the main checkout.
- Provider formats are private implementation details, observed on this Mac in September 2026. Other versions can provide less detail; missing evidence is not evidence of safety. Other users' processes and hosts that have not been added to Burro are outside coverage. Legacy Claude versions without session registries rely on process evidence and show reduced coverage.
- Historical Claude sessions are limited to records retained in the local session directory; Burro does not crawl all old conversations. Codex history includes unarchived database records. The detail pane shows up to ten inactive records per worktree.
- Local checks wake on provider file changes and otherwise run about every 3 seconds while a chat is working, waiting or uncertain, and every 15 seconds when all chats are quiet and the file watcher runs (3 seconds without it). Pages redraw only when a chat or notice they show changed.
- Local session titles and filesystem paths remain in memory/UI (other machines' last-seen chats are kept in the remote cache; see [Other laptops and servers](#other-laptops-and-servers)). Burro persists selected roots, comparison refs, discovery preference, manual protections, notch preferences, explicit remote host configurations, New chat defaults, the Orchestrator's daily sessions and Burro's own per-chat titles, pins, hidden chats and seen marks in `local.burro.worktrees` UserDefaults. On first launch after the Grove rename, it imports only the four original preference keys from `local.grove.worktrees` once, without overwriting existing Burro values. CLI JSON contains titles/paths and should be treated as local data. No telemetry is sent. Configured remote hosts receive only Burro's fixed scripts over SSH.

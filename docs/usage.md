# Burro

A small native macOS monitor for Git worktrees and Codex / Claude Code agents, with a live agent panel at the camera notch. Built with SwiftUI, Swift 6, a bundled Rust log worker, and system libraries. Requires macOS 14 or newer. Monitoring needs no additional accounts or hooks; optional usage limits use your existing provider sign-ins. Local monitoring stays on this Mac; remote monitoring uses SSH only for machines you explicitly add.

## Run

```sh
./script/build_and_run.sh
```

Source builds require Swift 6 and Rust through rustup; the repository pins the Rust toolchain. The script builds `dist/Burro.app` and its Rust helper, preserving the existing signing identity (ad-hoc on fresh setups without a certificate). You can launch that bundle directly or copy it to Applications. Other modes: `--build-only`, `--verify`, `--debug`, `--logs`, `--telemetry`.

```sh
./script/build_rust_worker.sh
BURRO_REQUIRE_RUST_WORKER=1 swift test
swift run burro-inspect --agents            # fast agent status, including unread results
swift run burro-inspect                     # JSON snapshot, automatic discovery
swift run burro-inspect /path/to/repository # limit to specified repositories
```

## Agent notch

Local Codex log inspection and Claude delegated-worker discovery/lifecycle parsing run in a private Rust child process, which reuses parsed lifecycle summaries while a file is unchanged. The app still checks live writer locks and event age on each poll. If that child fails, the existing Swift reader takes over and a later poll can restart it. Unverified chats remain protected and appear in Monitoring details, with a count in the notch footer. The active queue omits these rows by default; “Include idle and unverified chats” can show them alongside active chats. There is no separate service to install or configure; the worker exits with Burro.

- The notch is enabled by default. **Hover** over the black strip at the top of the screen to expand it; **click** to open or close; use the **pin button** to keep it open. Move away to collapse an unpinned panel, or use its chevron to collapse explicitly.
- **Agents / Usage / Mac** tabs stay visible in the expanded notch. Click a tab to keep it selected, including after closing and reopening the panel during this app session. Hover the other tab for 160 ms to preview it without changing your selection; move away to return. A Preview label and outlined tab distinguish temporary content. Quick crossings do not switch views; clicking during a preview commits it. Collapse/Escape clears any preview, while pinning keeps its existing meaning.
- A steady glow along the compact notch’s lower rim signals attention: **amber for input requests**, **blue for unread completed chats**. Input takes priority when both exist. The glow remains until the provider reports that input is handled or the result is read; hovering the notch does not acknowledge it. It uses short fades without pulsing, switches immediately with Reduce Motion, and adds no extra mouse-catching area. It follows both local and connected remote agents even when Usage is selected.
- The compact notch has two consistent status indicators: running agents on the left (waveform), and on the right the number of chats waiting on you in amber with an amber dot or, when none wait, unread results in blue. It has no logo, name, or idle count, and a side whose count is zero stays empty, so an idle notch is plain black (until the first check, both show "–"). When nothing is running but a task is scheduled, the left indicator becomes a teal clock and scheduled count.
- The expanded **Agents** tab has two sections. **Needs you** is a card per chat waiting on you: its title (click to open it), machine · folder, how long it has waited, the Brief's question when triage wrote one, and either a one-line reply field with **Send** or the single hand-off that works for it (**Open in Codex**, **Open in Claude**, **Attach in Terminal**, **Attach on <Machine>**, else **Open in Burro**). **Working** is one compact line per chat: its state, machine · folder and, when Burro saw the turn start, how long it has run. Chats that only have a result to read aren't listed; the footer's **N ready to read** counts them and opens Chats. Done results remain until the provider marks them read; merely opening the notch never acknowledges them.
- The quick reply decides and sends exactly as the Chats composer does: the same checks (for Claude, whether the session is open elsewhere, checked off the main thread and kept for a minute per chat and state) and the same send path, stopping an idle Claude background session first only when the composer would. When the Brief has a drafted reply for the chat, the field is prefilled with it, and sending it marks that draft as sent. A needs-you card is rebuilt whenever the chat it answers changes, and Send checks it still answers that chat. Sub-agents never get a reply field, only Open. A drafted reply is prefilled and follows the Brief until you edit it: it is replaced when the draft changes and cleared when it is discarded or sent elsewhere. If you edited a draft that was then sent or changed elsewhere, Send says "That draft was sent or changed elsewhere. Nothing was sent." and won't send that text until you change it. Return sends only text you typed or changed; send an untouched draft with the Send button. No reply field takes focus until you click into it. When Burro sent a reply but didn't hear back, the card says it may have reached the chat and empties the field. Burro never presses Send for you. While the field has focus or holds text you typed or edited, moving the pointer away doesn't close the panel; an untouched prefilled draft doesn't hold it open, and an explicit collapse (Escape, the chevron, opening a chat) still closes it.
- Chats are grouped by machine and checkout path (not branch or folder name), with explicit folder and branch labels. Unavailable remote branch metadata is labeled unavailable. Local checkout Git delivery uses cached refs and is never attributed to a single chat. Grouping preserves parent/worker links; workspace identities and sections stay fixed during pointer interaction. The options menu can include idle chats, refresh status, or open monitoring details.
- Codex workers with an explicit parent ID are folded beneath their parent chat. Others, including Guardian runs without that metadata, appear in a collapsed **Background workers** group per machine. Worker input requests promote the group and remain visibly labeled. Counts still represent unique agents, including working/waiting children; grouping does not discard safety evidence or infer ownership from a shared folder. Claude sessions without explicit parent metadata remain separate chats.
- While the pointer or keyboard focus is in the expanded panel, list positions and worker membership stay fixed; titles/status update live. New/disappearing items reconcile after interaction ends, or when **Update list** is chosen. A disappeared row is disabled rather than replaced under the pointer. Selecting a different filter deliberately refreshes the list.
- Click a chat to open it on Burro's Chats page. Hold ⌥ while clicking, or right-click → **Open in Codex** / **Open in Claude**, to open it in the provider's app instead; right-click → **Show in Burro** opens it on Burro's Chats page. **Settings → Chats → Open chats in Burro** (on by default) swaps the two: off, a click opens the provider's app and ⌥ opens Burro. A chat without a provider link always opens in Burro. Expand a worker group to open a specific worker. The footer arrow opens worktrees.
- The separate read-only agent poll runs independently of Git scanning: about 3 seconds after each sample while a chat is active or uncertain, and every 15 seconds when everything is quiet and the file watcher is running (file changes still wake it at once). A problem reading a provider's unread state is reported but doesn't keep the poll at 3 seconds. Footer notices name the affected machine and distinguish history coverage from connection failures. Click a notice for details, last successful remote check, and retry. Unknown/recent is not reported as confirmed running.
- Placement prefers the MacBook's notched display and reserves the camera's physical width. On every display, the black surface attaches flush to the physical top edge, including displays without a camera notch. Concave shoulders and rounded lower corners make it part of the screen edge, with no floating-window shadow. Layout updates when displays or Spaces change; the nonactivating panel joins other apps’ fullscreen Spaces and remains above them without switching apps or bringing the dashboard forward. It stays on your configured notch display; other displays do not get duplicate indicators.
- Hover opens immediately, including an 8-point approach area around the compact strip. The expanded panel has a 10-point edge tolerance and closes 120 ms after leaving. Returning cancels closing immediately. Passive pointer-movement observers work over Burro and other apps, independent of view tracking areas. Core Animation animates the outline and content fades, preserving motion through reversals while text stays at a fixed size. Deliberate collapse stays closed until the pointer leaves and returns. Opening with a click or keyboard does not silently pin the panel.
- **Settings → General → Agent notch** lets you disable the notch or prefer the main display. **⇧⌘B** opens it while Burro is active. It does not install a global keyboard shortcut or request accessibility/input-monitoring permissions. Clicking inside the panel does not activate the dashboard unless you choose an agent/worktree link.
- The notch deliberately uses a black surface to blend with the camera housing, with restrained sage and amber accents. It respects Reduce Motion and keeps monitoring when the dashboard closes.

Chat navigation uses `codex://threads/<UUID>` and Claude's existing desktop/bridge session IDs. These are navigation-only links: opening one does not send a prompt, import/resume a CLI session, or change remote access settings (replies are a separate, explicit action in [Chats](#chats)). Bare Claude CLI sessions without desktop/bridge metadata open their Burro details. Exact Code-session routes were checked against the installed apps; private provider routes can change. See [Claude's URL scheme documentation](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) for the public deep-link overview.

### Home

The Burro window opens on **Home**. Everything on it comes from the same live feed as the notch, and each chat is listed in one place only.

The left column, top to bottom:

- **The cover**: a greeting ("Good morning", "Working late"…) and one plain-language summary sentence.
- **Needs you** (amber): one card per chat waiting on you, newest first, then chats that ended a turn on a question without waiting. Sub-agents are never listed or counted here (they are answered through the chat that started them), as in the menu bar, notifications and Chats. Each card shows the title, machine · folder and agent · model tags, how long it has waited, and the question triage found or **Waiting for your approval**. When the chat has a drafted reply (triage's, or one the Orchestrator proposed), the draft is inline with **Send**, **Edit** and **Open**, and **Discard** on the draft. **Send** goes the way a proposal card's Send does (an idle Claude background session is stopped and continued with the reply, as its help says); **Edit** opens the proposal card in place. A draft whose Send Burro couldn't confirm has no **Send**: the card says it may have reached the chat, and **Edit** opens the proposal card with **Send again…** (behind a confirmation). Without a draft the card offers **Open** and the one hand-off that works (**Open in Codex** or **Open in Claude**). Burro can't answer an approval itself, so there is never an Approve or Deny button. Right-click a triaged card to **Dismiss** the Brief item. A question from a chat on this Mac that has since closed (it left Burro's list, which holds only open chats) is tagged **Closed** (**Not listed** for another machine's): its one button is **Open in Claude** when the Claude app still has the chat, otherwise there is no open button, a line says Burro can't open it, and **Dismiss** is a visible button; the Orchestrator's Brief queue does the same.
- **Working** (green): a grid of compact cards, one per chat working now (subagents belong to their parent): title, what it is doing ("Working in focustown", or the Brief's Stuck line), the machine tag, and how long the turn has run ("turn 18 min") when Burro saw it begin, otherwise when it last wrote ("active 4 min ago"). **Stop** appears where Burro can stop the chat (a Codex turn or a Claude background session), decided exactly as the Chats header decides it (for a Claude chat, from the same cached check of whether the session is open elsewhere, so no Stop shows until that check has answered), and runs only on that click; a chat the Claude app owns gets **Open in Claude** instead, and one running interactively in a terminal says **Stop it in its terminal**. A Stop's result line goes away when that chat's turn changes.
- **Ready to read** (blue): one card of rows, each with its one-line outcome (the Brief's Finished headline, else the reply preview an earlier scan already read; Home never reads a transcript for this) and its time. **Mark all read** marks them seen in Burro only; the providers' unread markers are never written.
- Each section shows up to five (Needs you) or six (Working, Ready to read) chats, then **Show all N in Chats**. With nothing in any of them, Home says "Nothing needs you and no agents are working."
- Then the [main project](#main-project), [benches](#benches) and projects as flat, monochrome cards; colour comes only from their live-count pills. Projects are your repositories plus any folder holding an active chat; each card shows live chats, worktree count, folders ready to clean and today's tokens. Click a project for its worktrees.

The right column: **Ask the Orchestrator** (see [The Brief](#the-brief)), **Today so far** (with activity tracking on), **To-dos**, **Machines**, **Notes** and the **Scratchpad**. Below about 900 points wide, the right column's cards move under Ready to read.

- **Machines**: one line per machine, this Mac first: a dot (green when Burro can reach it, grey when not), its name and its counts with its status line ("2 working · 1 needs you", "Unreachable since 14:02 · retrying in 30 s"). Click this Mac for Mac Health and another machine for Machines. The card reads only the checks Burro already runs.

"Tokens today" counts local Codex and Claude logs on this Mac since midnight, read by the bundled Rust worker in the background while Home is on screen (at most every 90 seconds). It is an estimate, like the Usage page's local history, and is hidden if the worker is unavailable. Home samples Mac Health only while visible, refreshes **Today so far** and the away figure every 2 minutes (one read of today's tracked day, and today's agent activity rescanned unless the last scan is under 100 seconds old) and starts no other polling; worktree inventories refresh on opening Home or Worktrees under the same rules as before.

Use the sidebar or **⌘1–⌘8** for Home, Orchestrator, Today, Chats, Worktrees, Machines, Usage and Mac Health. **⌘R** refreshes the current page. **Settings → General → Appearance** chooses Match System, Light or Dark; the notch always stays dark.

### Home and navigation

The window has its own sidebar on the left. From the top: the traffic lights and the sidebar button (drag this header to move the window; double-click to zoom); **Burro** with one line saying what your agents are doing ("2 need you · 5 working", or "All quiet"); then the pages in ⌘1–⌘8 order: under **Overview**, **Home**, the **Orchestrator** (a dot pulses while it works) and **Today**; under **Workspace**, **Chats** (count: chats that need you or have results to read; amber while any chat needs you, blue when there are only results to read), **Worktrees** (how many the last scan found) and **Machines** (how many, once you've added another machine); under **System**, **Usage** and **Mac Health** (count: leftover processes; a green dot while the Mac is kept awake). **The crew** lists the chats at work right now, one line each: those that need you (in bold, amber dot), then those working (green dot), then those with a result to read (blue dot), newest first; sub-agents aren't listed. Up to 12 show, with **Show all N in Chats** after them; hover a row for its project and machine, and click it to open the chat. **Settings** sits at the bottom. The current page's row is highlighted (the Timeline highlights Today). Hide the sidebar to an icon rail with its button or **View ▸ Hide Sidebar** (⌃⌘S); Burro remembers. The rail shows the same pages as icons and up to six crew avatars with their state dots. When the window is too narrow for the full sidebar beside a page at its full layout (under about 1,125 points wide), it shows the rail by itself; showing the sidebar then opens it until the window widens again, without changing what Burro remembers. Above each page, a slim strip holds a back pill on the left and, on the right, the page's tools (on Worktrees: search, Cleanup, Add a repository; Refresh on Worktrees, Today and Machines), a search field ("Search chats, or type to start one ⌘K") that opens the [command palette](#home-and-navigation) on a click (it is a button; typing happens in the palette; a magnifier when space is short, and always on Worktrees), and **New chat** (⌘N), the window's one amber button, far right; drag the strip to move the window too.

- **Back and Forward**: ⌘[ and ⌘] (also in the **Go** menu) step through the pages you've shown, like a browser. When you reach a page from inside another (opening a chat from Today or Home, say) rather than from the sidebar, a shortcut or the menu bar, a **‹ Today**-style back pill appears at the left of the strip above the page and returns to where you started; the Timeline shows **‹ Today** too.
- **⌘K** (**View ▸ Command Palette…**) opens a search over the main window: pages, every chat on every machine (the Chats list), projects and machines, plus a few actions: **New chat…** (or **New chat in** a project, which opens the New chat sheet with it selected; **New chat on <Machine>…** and **New chat in <folder> on <Machine>…** for your other machines, listed below this Mac's), **Start chat: "…"** for whatever you typed (it opens the New chat sheet with that text as the prompt; it is the only row when nothing else matched, otherwise the last), **Open Settings**, **Refresh** the current page, **Keep awake for 2 hours** (or **Stop keeping awake**) and **Ask the Orchestrator about** a chat, which puts the question in the Orchestrator's composer (after anything you'd written) without sending it. Type to filter; chats that need you rank first, then working chats. ↑/↓ move, Return runs, Escape or a click outside closes it. Nothing in it messages or starts an agent by itself. When the Notes window is in front, ⌘K is its own action list.
- **Window ▸ Burro** (⌘0) reopens the window after you close it; the notch and menu bar keep running without it. Clicking Burro in the Dock does the same.
- **Menu bar**: the Burro icon alone when nothing is running, the icon and a count while agents run, and a needs-you glyph with the number waiting while a chat needs you (menu-bar items have no colour). Clicking it opens a popover, top to bottom: a one-line **Start a chat…** field (Return opens the New chat sheet with the text as its prompt, in the current project; nothing starts until you press Start there), **Needs you · N** with up to five chats waiting on you, newest first (clicking one opens it like a notch row: in Burro, or in its provider app with ⌥ or with **Open chats in Burro** off), **N drafts ready** with **Review** when the Orchestrator has replies drafted for you to send (it opens Home; the menu-bar label doesn't count drafts), **Keep awake**: a clock menu with **For 1 hour**, **For 2 hours**, **For 4 hours** and **Until I stop** (and **Stop keeping awake** while a request runs), the **While agents work** switch, a status line (how many chats on this Mac work now, " · lid closed" when a closed lid is covered) and a **Stop keeping awake** row while a request runs; these act on the Mac, never on agents. Then **Open Burro**, **Today** (with today's focused time when activity tracking is on, read each time the popover opens), **Chats** (what is working or waiting), **Notes** (⌥P when that shortcut is on) and **Show notch** (⇧⌘B), and a last line with **Settings…** and **Quit Burro** (⌘Q). **⇧⌘B** (in the app menu) shows the notch.

Home sits on an ASCII aquarium that stays put while the page scrolls over it. Your agents are the fish. The species comes from provider and model: Claude Opus is a shark, Fable a sailfish, Sonnet a barracuda and Haiku a minnow; Codex's Sol models are tunas, Astra models angelfish and other GPT models pufferfish. Subagents are small fry that swim beside their parent. Effort sets the variety: low effort darts about with small plain fins, while higher effort glides slower with longer fins, stripes at Extra High and spots at Max (or Ultra). Size is age: a new chat starts as a small fish and grows over its first day. A chat that needs you turns amber and waits at the surface. Scheduled chats, waiting on a timer, are jellyfish that drift almost in place and pulse; their tentacles grow longer with effort. Every other chat from today (idle, done or closed) swims too, darker, so the tank shows the whole day; up to 24 fish, 16 fry and 5 jellyfish, with chats that need you or are working first. Hover a fish or jellyfish in the open water between cards to see its chat, model, effort and age, and click it to open the chat. Model and effort come from Codex's thread index and the end of Claude's transcript, so they show only when the provider records them. The tank animates a few frames a second, only while Home is on screen, and holds still with Reduce Motion. The backdrop button (**Change the backdrop**) picks **Aquarium**, **Glyphs**, **Pixels** or **Photo** (any image or your desktop picture), the last three across the top of the page. On the right, **Notes** (click + or a note to open it in the Notes window) and a **Scratchpad** that saves as you type. There is no dock: New chat is at the top right of the window, and ⇧⌘B still shows the notch.

### Startup and notifications

**Settings → General → Open at login** makes Burro a login item. When macOS opens it at login, Burro starts quietly: the notch, menu bar and activity tracking run, but it doesn't come to the front or show its window. Click Burro in the Dock, open it again, or use the notch, menu bar or ⌘0 to bring the window back. Burro tells a login launch from a normal one by the launch event macOS sends.

**Settings → Notifications** has two switches, both off: **Notify when a chat needs you** and **Also when a chat finishes**. Turning one on asks macOS for permission; if it's turned off in System Settings, the section says so with **Open Notification Settings…**. A banner is posted once per chat when it has been waiting on you (a question or an approval, on any machine) for about 5 seconds, or, with the second switch, when a chat Burro saw working finishes with a result to read. The banner names the provider, folder and machine, and the chat's title; it is removed once the chat stops waiting or the result is read. A needs-you banner goes out without waiting for the Orchestrator; when [triage](#the-brief) later writes a headline for that chat, a banner still on screen is replaced in place, quietly, with "<title>: <headline>". Click it to open the chat on the Chats page. A chat that is already waiting the first time Burro sees it (at launch, when a remote machine connects, or when one comes back after being unreachable or after sleep) doesn't notify until it leaves that state and comes back, and a machine dropping out doesn't withdraw a banner or post it again. Subagents never notify, and banners left over from a previous run are cleared when Burro starts. Notifications only read chat state; they need the bundled app.

### Settings

**Settings** (⌘, or **Settings…** in the menu bar's popover) has a sidebar of eight panes. Each pane has a title, a sentence on what it covers and cards of controls; every control stores the same preference it always did.

- **General**: **Appearance** (Theme), **Open at login**, **Agent notch** (on or off, and **Prefer the main display**), **Open Notes with ⌥P from any app**, **Show usage limits** (with **Connect Claude**) and **To-dos** (sync with Maurice: **Import from Maurice**, or enter the deployment manually; **Sync Now** and **Disconnect** once synced).
- **Chats**: **Open chats in Burro**.
- **Orchestrator**: automatic triage, its cap and when it pauses, the morning brief, the model and effort for your questions, notes access, memory and what it can read (see [The Brief](#the-brief)).
- **Activity**: **Record activity** (the same switch as Today's Turn on / Turn off, with **Resume** while paused), **Count me as away after**, **Read the site in Arc and Chromium browsers**, and **Write Shipped summaries with Claude**.
- **Machines**: this Mac's [Keep awake](#keep-awake) controls and **Other laptops and servers** (see [Other laptops and servers](#other-laptops-and-servers)).
- **Notifications**: **Notify when a chat needs you** and **Also when a chat finishes** (see [Startup and notifications](#startup-and-notifications)).
- **Privacy and data**: **What leaves this Mac**, one line per channel worked out from the real switches ("Chat endings go to Claude Haiku 5.5 for triage" or "Triage is off, so no chat endings are sent", the same for Shipped summaries, what the Orchestrator is sent when you ask it something, usage limits, to-do sync, "Nothing from tracked activity is sent anywhere", and which machines SSH connects to). **Stored on this Mac** lists where Burro keeps its data, each with its existing action: **Delete all activity…** and **Clear quota history…** (each asks first), **Clear all caches** for other machines' chats, or **Show in Finder**. The same "What leaves this Mac" card sits beside the Orchestrator pane on a wide window.
- **Advanced**: **Discover repositories automatically**, **Added repositories**, **Comparison branches** and **Rescan**.

### Main project

Home features one project: the repository with the most worktrees, or the one you choose from the card's **⋯** menu. The card shows how many chats are running or need you in it on every machine, its worktrees, folders ready to clean and today's tokens, a **Live** column (working, waiting and unread chats) and **Earlier today**. **New chat** opens the New chat sheet with that project selected; **Worktrees** filters the worktree list to it. It is left out of the project grid below.

### Chats

**⌘4** (or **Chats** in the sidebar) shows three panes: the list, the open chat and, when the window is wide enough, the details panel.

**The list** has every Codex and Claude chat Burro sees, on this Mac and your SSH machines. At the top, a **Filter chats** field: press **/** while no text field has focus to put the cursor in it; it matches titles, folders and machine names, **claude** or **codex**, and model names such as **opus**. Chats you just started appear in a **Starting** group until the real chat shows up (see [New chat](#new-chat)). Chats you pinned that aren't asking for anything sit in an unlabelled group above the sections; then **Needs you** (amber), **Working**, **Ready to read** (a pinned chat in one of these stays there, on top) and **Earlier**, newest first, each headed with its count ("● NEEDS YOU 2"). Earlier shows its 12 most recent chats and a **Show all N** row (all of them while you filter, or when the open chat is further down). Every row has the same two lines beside the chat's agent: the Burro mark in Claude orange or Codex blue (dimmed for idle chats) with the state as a small dot on its corner (amber needs you, green working, blue ready to read; idle chats have none), and the title (a pinned chat's pin at its right end); under it the place and the time, such as "focustown · 4 min" for this Mac or "Studio · focustown · 21:17" for another machine. Times read "now", "4 min", "21:17", "Yesterday", "Mon" or "3 Nov"; a working Claude chat says how long it has been working ("for 36 min", "since 13:09"), because Claude only records when a chat's status changes, not each thing it writes. Needs you and Ready to read rows add one line of the chat's last reply, as plain text, when Today's activity scan has already read it (chats on this Mac only; Burro doesn't read each chat's file just for the list). Working, ready and needs-you titles are bold; idle ones are lighter, so the bottom of the list recedes. A row always shows the state of the section it is in. The selected row is filled and carries its state's colour on its leading edge.

**The header** of the open chat has its title with a state chip (**Needs you**, **Working**, **Ready to read** or **Idle**), one quiet line such as "Claude · Opus 5.5 · This Mac · focustown · turn 18 min" (the turn clock runs from the latest message you sent, only while the chat works), the offline line for a remote chat shown from Burro's copy, then **Stop** (⌘.) while Burro can stop the chat, or **Stop it in Claude** when only the Claude app or a terminal can, the **⋯** menu and the details-panel toggle.

A chat opened from the Brief or a notification that isn't in the list (chats on this Mac appear only while they are open in Claude or Codex) shows **This chat isn't in Burro's list** instead of a blank pane, with **Open in Claude** when the Claude app still has it.

Pick a chat to read it. A long opening brief (like a session another chat started) shows as a **Task** card with **Show more**. Each turn shows your message, then a **Worked for 3m 9s** line that stays open while the chat works: the agent's notes, runs of tool calls folded into one line such as **Ran 5 commands, read 2 files** (open it for each call; click a call for its output), delegated subagents on their own line, and the plan as a checklist card (done, in progress, to do). Then comes the reply with Markdown, code blocks, tables (a quiet grid with a bold header row; a table wider than the conversation scrolls sideways), and any images or videos the agent linked (`![caption](/path/file.mp4)`). Codex's app markup never shows as raw text: an inbox item (`::inbox-item{…}`) becomes a one-line note with a tray glyph, its title and its summary; a code comment (`::code-comment{…}`) a note with its title, body and file and lines; a writing block keeps its text without its `:::` fences; other directives are left out. The same lines are left out of the list's and Home's one-line previews, where an inbox item shows as its title. This is display only: nothing sent to or kept for the chat changes. Media on this Mac loads in place; from another machine, images up to about 8 MB copy over SSH automatically, and larger images and videos when you click (see [Other laptops and servers](#other-laptops-and-servers) for where copies are kept). Click an image to open it. **Open in Codex/Claude** appears when the provider has a link.

**Following a live chat.** While a chat is working or waiting and on screen, Burro re-reads it every 2 seconds on this Mac (every second while a reply you sent isn't in its log yet) and every 4 seconds on another machine. On this Mac the Rust worker parses only what the file added since the last read, so an unchanged chat costs almost nothing; on another machine only the new bytes travel (see below). The page follows new messages while you're at the bottom; scrolled up, it stays where you are and offers **↓ N new**. While the chat works, a strip at the bottom says what it's doing right now, using the tool call's own description when it gave one, and for how long. When the chat waits on you, **Jump to last question** (⌘↑) scrolls to it, and the conversation ends with a **Waiting for you · 4 min** card that says what Burro can and can't do about it (it can't answer an approval: neither provider offers a way) and gives the one action that reaches the place that can: **Open in Codex**, **Open in Claude**, **Attach in Terminal** or **Attach on <Machine>**. A reply you send shows at once, dimmed as **Sending…**, until the chat's own log has it (an echo the log never shows within a few minutes is dropped, as is one whose send failed).

**Reply** from the composer at the bottom: the message field, then one row with the paperclip and the access, model and effort menus on the left and **Send** (↩), the composer's one amber button, on the right. Return sends, ⌥Return adds a line. When Burro sent a reply but didn't hear back (no answer in time, or one it couldn't read), it says the reply may have reached the chat and empties the field, so a second click can't send it twice by accident (**Put my text back** returns it once you've checked the chat); a sub-agent has no reply field (answer it through the chat that started it). Each option starts as "keep what this chat uses":

- **Access**: Ask me, **Approve for me** (Codex reviews its own approval requests), Edit freely, or Read only.
- **Model** and **Effort**: Codex's list comes from its app server on that machine; Claude offers Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.2 and Fable 5.1.
- **Attachments** (chats on this Mac only): drop or paste files and images, or use the paperclip (**Choose Files…**, **Paste File or Image**). Up to eight per message, each a regular file of at most 20 MB, never from credential folders such as `~/.ssh`, `~/.aws` or the Keychains folder, nor Codex's and Claude's own sign-in files. Codex receives images as images and other files as paths in the message; Claude receives every path in the message and reads the files itself. Pasted image data is first written, owner-only, to Burro's temporary folder.

**Stop** (⌘.) sits in the chat's header while the chat works: it ends the running Codex turn (`turn/interrupt`) or stops a Claude background session (`claude stop`), on this Mac or another machine; the conversation is kept. A Claude chat running in the Claude app or a terminal can't be stopped from outside: the button reads **Stop it in Claude** and opens it there. The header and the composer decide this from the same checks, so they never disagree, and Stop's result shows above the composer.

While a chat is working, the composer's Send gives way to:

- **Queue for when it's done** (Return): holds your message and sends it once the chat has looked idle for a few seconds, through the same path and checks as a normal reply. One queued message per chat; it shows above the composer with **Edit** and **Cancel** until it goes. It is dropped with a notice (and its text kept, so you can edit it back) if the chat disappears for a minute, turns out to be open elsewhere, or is still busy a day later. A message is marked as sending before it goes, so one found marked after Burro quit mid-send is never sent again; you're told to check the chat instead. Queued messages are kept in `~/Library/Application Support/Burro/reply-queue.json` (owner-only).
- **Steer now** (Codex only): adds your message to the turn Codex is on now (`turn/steer`). If that turn has already ended, Burro says so; send it as a normal reply.

For a Claude chat, Burro first checks whether the session is open elsewhere; until that first check answers (usually well under a second; at once when you come back to a chat Burro already checked), a quiet empty bar holds the composer's place and the **Waiting for you** card waits too, so a reply field never appears and then turns into the bar below. Codex chats don't wait. Text put in the field meanwhile is kept.

When nothing can be typed, the composer is a single compact bar instead of a field: the reason in a sentence and, on the right, the action that helps (left out when the **Waiting for you** card above already offers it): **Open in Claude** (the chat is open in the Claude app or a terminal), **Attach in Terminal** (`claude attach` for a Claude background session on this Mac that can't take a reply now), **Attach on <Machine>** (the same over SSH, opened in Terminal), or why the machine can't take replies now.

Codex replies go through Codex's app-server daemon: Burro resumes the thread and starts a turn. On another machine the same happens over SSH, which needs Codex's standalone install there (the daemon only runs from it); Burro tells you if it's missing. Claude replies run `claude --bg --resume <id>`, which continues the conversation in the background under the same id. That only works when nothing has the session open, so Burro checks `claude agents` first:

- Nothing has it open (including background sessions that already finished): the reply goes straight away.
- Its **background session is still open but idle** (how `claude --bg`, and so every chat Burro starts, is left after its turn): **Send** (its help says so) stops that one session with `claude stop`, waits until `claude agents` no longer lists it as running (a few seconds at most), then resumes it with your message. This happens only for the chat you're replying to, only when it isn't working or asking anything, and only when no `claude attach` for it is running. If the stop fails or can't be confirmed, nothing is sent and the reason is shown. A queued message for such a chat goes the same way. On another machine the fixed `remote_reply.py` script does the same checks there.
- Open in the Claude app or a terminal, or a background session that is busy or waiting for an approval: Burro says so instead of starting a copy, and never stops it.

Approval prompts from a reply wait in the agent's own app (or `claude attach`) and show as **Needs you** in Burro. The live behaviour of stopping, steering, queuing and continuing against real Codex and Claude sessions, and on a real remote Mac, follows the providers' documented commands but hasn't been exercised end to end.

**Managing chats.** A row's context menu starts with **Ask the Orchestrator about this chat**, which opens the Orchestrator page with "What's the latest on “<chat>” (<machine>)?" in its question field, after anything you had written there; nothing is sent until you click **Ask** (Return sends only once you've typed or changed something). The **⋯** menu in a chat's header (which also has **Refresh**), and a row's context menu, have **Rename…** (a Codex chat is renamed in Codex; a Claude chat gets a title only Burro shows, with **Use Claude's Title** to go back), **Pin to Top** / **Unpin** (Burro only), **Mark as Read Here**, **Open in Codex/Claude**, and **Archive in Codex…** (asks first; it leaves Codex's list and Burro's, and Codex can unarchive it) or, for Claude, **Hide in Burro** (it comes back by itself when the chat has new activity). Titles, pins and hidden chats are kept in Burro's preferences.

**Seen here.** Opening a chat on this page (or **Mark as Read Here**) marks its result as seen in Burro: it stops counting as ready to read in the Chats list and badge, on Home and in the notch, until it has new activity. A chat counts as seen only while Burro is the active app with the Chats page in its focused window, and a seen mark never suppresses a notification or the Brief's triage for that chat. Only Burro's own copy changes; the providers' unread markers are never written, so the chat can still show as unread in Codex or Claude. Up to 2,000 seen marks are kept in Burro's preferences.

**Drafts.** When the Orchestrator has a reply drafted for a chat (from [triage](#the-brief) or because you asked), one line above the composer shows it: **Draft from the Orchestrator: …** with **Use**, which puts the whole draft in the composer for you to edit and send the usual way (it never sends, and takes the draft off the Brief), and **Discard**.

**Details panel.** The panel on the right (toggle it with the button at the end of the header, **Show details** / **Hide details**; it shows when the window is wide enough) has:

- **Folder**: the worktree's branch, "4 uncommitted · 2 unpushed", the path and, for a worktree on this Mac, **Open worktree** (the Worktrees page with it selected) and **Review cleanup…** (the usual cleanup confirmation).
- **Changes**: each file the branch changed with its added and removed lines, largest first, and the file count in the header. It is a read-only `git diff --numstat` against where the branch left its base (the merge base with the scan's base, or with origin's HEAD, then `origin/main`, `master`, `staging`), committed or not; untracked files aren't in a diff, so they're only counted as uncommitted under Folder. This Mac only; for a remote chat it says where the chat runs.
- **Context**: "124K of 200K" over a meter when the model's window is known (Codex records it), otherwise the tokens.
- **Cost so far**: the chat's tokens valued at the same API list prices the Usage page uses, such as "$3.84", never a bill. Burro reads only the token counts in the chat's own transcript, skipping conversation text, and only what was added since the last read. It shows "—" for a chat on another machine, a transcript over 64 MB or a model without a known price. Beside it, **Started**.
- **Background tasks** still running.

Changes and cost are read off the main thread when the panel appears and again as the chat writes (at most once a minute), and kept per folder and chat in memory, so reopening a chat shows them at once.

Burro shows the latest 300 messages, read from at most the last 16 MiB of the chat's file; older ones say so at the top. On this Mac the Rust worker finds and parses the file in its own process (separate from history scans, with a 10-second deadline), keeping the parsed messages of the last eight chats it read in memory, never the raw file. A chat on another machine is read through Burro's local copy of its transcript (below); without that copy, a fixed read-only script (`remote_transcript.py`) fetches it in full over your SSH connection. Clicking a chat anywhere else in Burro (Home, Today, Machines, the ⌘K palette, a notification, and the notch and menu bar with **Open chats in Burro** on) opens it here.

**Chats on other machines.** The first time you open one, Burro copies the end of its transcript (the last 4 MiB, starting at a line) into its remote cache and shows it; the next time it opens at once from that copy and then catches up. A live remote chat fetches only the bytes added since the copy (a check that finds nothing new returns a header of about 120 bytes); a replaced or rewritten file starts the copy over. While the machine can't be reached, the copy stays readable with a line such as "As of 14:02 · Mac mini unreachable · retrying in 30 s" (or "no longer on Mac mini" when the transcript is gone there), and catches up as soon as monitoring reaches the machine again. When the copy doesn't start at the beginning, **Show earlier messages** at the top fetches more of its history (the copy never grows past 16 MiB that way) and shows up to 500 messages. The reading is done by the fixed read-only script `remote_tail.py`, which opens only that chat's transcript under `~/.claude/projects`, `~/.codex/sessions` or `~/.codex/archived_sessions` there. Where the copies live and how long they're kept: [Other laptops and servers](#other-laptops-and-servers).

### Orchestrator

The **Orchestrator** is one Claude Code chat that Burro runs for you, and keeps the [Brief](#the-brief). Open its page with **⌘2** or **Orchestrator** in the sidebar, or ask from **Ask the Orchestrator** on Home: what needs you, where a project stands, what a chat on another machine did, or to draft a reply or a new chat. Return sends; ⌥Return adds a line; the stop button ends a turn. The **Model** menu by its composer picks the Claude model (Fable 5.2 by default; Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 too) and the **Effort** menu how hard it thinks (Low to Max, High by default); both apply from your next message. Its big model runs only while it answers a message you sent; the automatic reading of chats behind the Brief is a separate, small model (below).

**One conversation a day.** The first question of a local day starts a fresh conversation, and later questions that day continue it, so its context never grows without bound. The conversation card's **⋯** menu has **New conversation** (another one today), **Let it read my notes** and **Earlier days** (the last 30 days); choosing an earlier day shows that conversation with a **Back to today** bar.

Under the page's title, one line says what the Brief holds and when triage last ran ("2 need you, 3 finished, 1 stuck · last triage 3 min ago"), with **Run triage now**: it reads the newest chats waiting on you or unread (up to 30) and triages up to five whose latest messages haven't been triaged since they last changed, newest first, at once (they go ahead of anything already queued), counted toward today's cap and through the same gate as automatic triage (with triage Off, over a cap or under Claude's limits it queues nothing and says why). When every chat it looked at is already triaged it says **Nothing new to triage**; otherwise "Triaging N chats now". Then three tabs, **Brief**, **Memory** and **Runs**:

- **Brief**: three columns. On the left, the Brief queue: **Needs you** (amber), one card per chat with its title, machine and age, the question it ends on and, when the chat has a draft, the draft inline with **Send**, **Edit** and **Discard** (Send goes the way a proposal card's Send does; Edit swaps in the full proposal card); a chat without a draft offers **Open**. **Finished**: one row per chat with its one-line outcome, each opening the chat, and **Mark read**, which marks those results read in Burro only and clears them from the Brief. **Stuck**: the chat, how long it has been quiet and where, with **Open** (nothing here nudges an agent). Right-click any item for **Ask the Orchestrator about this chat** (it only fills the question; nothing is sent until you click **Ask**) or **Dismiss**. A draft or proposal whose Send Burro couldn't confirm (the machine or Codex didn't answer in time, or answered in a way Burro couldn't read) is marked **May have gone**: it says the chat may have started or the reply may have arrived, offers **Open Machines** (a chat started on another machine) and **Open Chats** to check, and **Send again…** only after a confirmation that a second chat may be started (or the chat may get the reply twice); it never goes back to a plain Send, and the Orchestrator can't propose the same thing again. The Orchestrator never proposes a reply to a sub-agent: it is told to address the parent chat. In the middle, today's conversation: one turn per question, your message, a one-line summary of what it checked (click to open the timeline of steps and their output; it stays open while it works), its answer, and under it any proposal cards and to-do changes, then the composer with its model and effort menus and the reminder "Proposals wait for you before anything starts". On the right, **Memory** (the first standing notes, a field that adds a global note on Return, and **All N**, which opens the Memory tab) and **Budget** (triage runs today of the daily cap, today's cost of the Orchestrator's and triage's runs, Claude's session and weekly windows as meters with when they reset, amber below the floor where triage pauses and hidden while Burro doesn't know them, the floors in words, why triage is paused if it is, and the automatic-triage switch). Below about 1180 points the side cards move under the queue; below about 860 everything stacks in one column.
- **Memory**: standing notes it is given at the start of every answer, global ones first, then your main project's, each marked as yours or noted by it. Add a note (global or for a project), edit one in place or delete it. It adds its own with `remember` and drops them with `forget`. The list starts with one note, "End answers with a one-line TL;DR.", added once. It no longer reads your own Claude Code settings or CLAUDE.md files.
- **Runs**: how many model runs it made today and what they cost, then the latest runs with their trigger (a question you asked, a triage batch or the morning brief), model, time taken and tokens. Costs are what Claude Code reports at API prices; on a subscription the runs count toward your usage windows instead.

**Proposed replies and chats.** The orchestrator never sends a message or starts a chat itself. When it drafts a reply to a chat (on any machine) or a new chat (on this Mac, or on another machine in a folder Burro knows there), the draft appears as a card under its answer: one line saying what will happen ("… on devbox" for another machine), the full text to edit in place, and **Send** or **Discard**. A waiting card is outlined in amber (**Needs your OK**). Nothing goes out until you click **Send**: a reply goes through the same path as the Chats composer (keeping that chat's own access, model and effort, and continuing an idle Claude background session as Send does there), a new chat through the same launch as New chat (Ask before acting unless the proposal names another access level; on another machine the folder, Claude's trust and the install are checked there when you click). The card then shows Burro's confirmation, or the error, in which case it stays unsent. If the chat is no longer waiting for you the card says so and the button reads **Send anyway**; if Burro can't see the chat, or a new chat's folder is gone, it can't be sent. Proposals survive a relaunch and expire a day after they were made: an expired card can only be discarded, and any proposal leaves the file after a week. Replies triage drafted are listed under **Drafted by triage**, and proposals no visible turn shows (from an earlier conversation) under **Proposed earlier**.

**To-dos it changes.** `add_todo` and `complete_todo` don't wait for Send: Burro applies them to today's to-dos at once (added ones are marked as the Orchestrator's) and shows a line under the turn, "Added to-do … · Undo" or "Completed … · Undo". Undo is offered for a day; a change that couldn't be applied says why.

**How it runs.** Burro runs it with `claude -p` in `~/Library/Application Support/Burro/Orchestrator`, with no user or project settings (so no hooks, permission rules or CLAUDE.md) and only Burro's MCP server, not your other MCP servers. Claude Code's built-in tools are switched off except the loader for deferred tools, so it can't read or edit files itself, run commands, browse the web or start sub-agents; anything else is denied rather than asked. Its brief, today's date and its memory go in as an appended system prompt each turn. Its tools come from the bundled MCP server (`burro-mcp`), which reads a snapshot Burro writes before and during each turn:

- **brief**: the Brief's open items, with kinds, questions, drafted replies and age. Its instructions tell it to call this first and answer from it.
- **overview**: machines and agent versions, folders it can start chats in on other machines, the main project, projects, chats by status with their subagents (chats already in the Brief are only counted), and today's to-dos.
- **list_chats** (filter by status, machine, project or text), **chat_digest** (a chat in a few lines: triage's reading when there is one, its last ask and answer, the question it ends on and its worktree's state, without diffs) and **read_chat** (any chat on any machine, read the same way as the Chats page; it ends with a cursor, and `since` returns only what's new after it).
- **list_worktrees**, **read_shipped** (Burro's cached Shipped summaries; it never runs `gh`), **usage** (what's left of each Claude, Codex and Grok window and when it resets).
- **read_notes**: your notes, only when **Let it read my notes** is on in the page's **⋯** menu (off by default).
- **read_file** and **search_files**: text files in your git repositories and their worktrees on this Mac, nothing else (a chat's working folder that isn't a repository is not readable). All of `~/Library` and every hidden file or folder directly in your home folder (`~/.config`, `~/.netrc`, shell history and the like) are always off-limits. A file is readable only when the path actually opened (checked on the open file, so links and `..` can't get around it) lies inside a repository or worktree folder from Burro's snapshot and outside Burro's own data (`~/Library/Application Support/Burro`, which holds tracked activity, notes and its own files, and `~/Library/Caches/Burro`), `~/.claude`, `~/.codex`, `~/.ssh`, `~/.gnupg`, `~/.aws` and the Keychains folder. Files shaped like secrets (`.env`, private keys) and git internals are refused, the home folder itself is never a root, reads are capped and searches skip build and dependency folders.
- **reply_chat** and **start_chat** (with an optional `machine`): record a proposal; nothing is sent.
- **add_todo** and **complete_todo**: record a to-do change that Burro applies at once with Undo.
- **remember** and **forget**: edit its memory.

Its folder holds `state.json` (the snapshot: chat titles, paths, machine names, worktree facts, to-dos, cached Shipped summaries and usage windows, your notes only when allowed; no message bodies, credentials or tracked activity), `actions.json` (proposals and to-do changes), `brief.json` (the Brief), `memory.json`, `runs.jsonl` (one line per run, kept 30 days and at most 2 MB), `mcp.json` (the tool server's configuration) and the `Triage` folder triage runs in. All are owner-only; files both Burro and `burro-mcp` write are changed under a lock. A short turn takes about 5–15 seconds and is billed to your Claude account like any Claude Code chat.

### The Brief

The **Brief** is what your chats need, kept current between questions by [triage](#the-brief). It holds three kinds of items: **Needs you** (the question a chat ends on and, when a short reply would unblock it, a drafted reply; it also catches chats that ended a turn on a question without waiting), **Finished** (a one-line outcome) and **Stuck** (a chat working with no sign of life: no new output for 45 minutes, or three hours while one tool call is still running or when only a status time can be seen, such as a Claude chat on another machine; this needs no model call).

It no longer has its own card on Home. Its items appear where the chat already is: Needs you items (with their drafts and **Send**, **Edit**, **Discard**) on Home's **Needs you** cards, Finished headlines as the outcome line under **Ready to read**, and Stuck lines on the **Working** cards (see [Home](#home)). The whole Brief, with **Mark read** and the Stuck list, is the left column of the [Orchestrator page](#orchestrator). Right-click an item there, or a triaged card on Home, to **Dismiss** it. An item resolves on its own when its chat moves on (works again, shows new activity, or stops waiting with nothing left to read); a newer reading replaces it, and items leave after seven days.

Home's **Ask the Orchestrator** card keeps the rest: the composer, always open (Return sends a question you typed or changed to the Orchestrator, which only ever proposes work; an untouched **Ask the Orchestrator about this chat** prefill goes only by the send button or **Ask**), a line for proposals it made in conversation that wait for you, what it is doing now or its last error, a link to its last answer with its age (never the answer's text), its setup problem, and the triage footer: "Triage: 9 today · On", "· Off", or why it's paused, with "Reading N chats…" while triage runs; the footer turns automatic triage on or off. The card's header opens the Orchestrator page.

**Triage.** When one of your chats starts waiting on you or finishes a turn (on any machine; subagents excluded), Burro queues it. A batch goes 30–45 seconds after the first chat (sooner once five are waiting) as one `claude -p` call to Claude Haiku 5.5 through your signed-in Claude Code CLI, at low effort, with no tools, MCP servers, settings, hooks, CLAUDE.md or saved session, run in the Orchestrator's `Triage` folder (so it never shows as a chat). One call at a time, at most five chats each. For each chat it is sent only the title, project and machine, the last message you wrote (up to 2,000 characters), the last assistant message (up to 4,000), the last five tool lines and the Orchestrator's memory notes for that project, all marked as data; nothing from activity tracking, and any path into Burro's Activity folder is blanked. The end of each transcript is read on this Mac or over SSH as Chats does, and a chat whose last messages were already triaged is skipped. It answers whether you're needed (a decision, a blocker, a failure, a loop) or the chat is done, with a headline and, when a short reply would unblock it and it is confident enough, a drafted reply in your voice. A draft is only ever a proposal in `actions.json`: you Send, Edit or Discard it on the Brief, take it into the composer with **Use** in Chats, or ignore it. Drafts also show in the menu bar (**N drafts ready**).

Limits: automatic triage is on by default and runs at most 150 times a local day (**Daily cap** 25, 50, 100 or 150 in Settings) and 30 times an hour, and pauses itself while Claude's session window has under 15% left or its weekly window under 10% (when Burro knows them). The **morning brief** (on by default) triages chats still waiting on you or unread from the last day, up to five, once a day on the first activation after 5 am. Every triage run is logged in `runs.jsonl` with the Orchestrator's own runs, so the footer and the Runs tab agree, and counts toward your Claude usage. Triage against real chats and real Haiku runs, and the banner updates, are implemented as described but haven't been exercised end to end.

**Settings → Orchestrator** has **Automatic triage** (the same switch as the footer) with its **Daily cap** and today's count and when it **Pauses itself**, **Morning brief**, **Model and effort for your questions** (the same choices as the page's menus), **Notes access**, how many memory notes it keeps with a button to the Memory tab, and **What it can read**. On a wide window "What leaves this Mac" (see [Settings](#settings)) sits beside them.

### Benches

Benches group projects the way you think about them. Choose **Group into benches** (or **New bench** once you have some), name it, pick an icon and colour, and tick its projects. Home then shows your benches with their combined running, needs-you and to-read counts (or today's tokens when they're quiet), and the projects that aren't on a bench below them. Click a bench to see its worktrees (the Worktrees page says "Showing only <bench>", with **Show every repository**); right-click to edit or delete it. A project can sit on more than one bench.

### Machines

**Machines** (⌘6) has one card per machine you work on: this Mac and every SSH machine you added. The header reads "2 of 3 reachable · 3 chats working · 2 need you" with **Check all now**, which checks every machine's chats and tools at once. Each card shows:

- The name and OS, the machine's status line ("Connected · checked 12 s ago") with its working and needs-you counts, and a pencil that opens the machine editor.
- **Chats here** / **Chats there**: the chats working or waiting for you on that machine, needs-you first, newest first (subagents and expired remote samples left out). A row opens the chat in Chats. A Claude chat on another machine also offers **Attach**, which first checks on that machine (read-only) that it is a background session, then opens `claude attach` there in Terminal.
- **Harnesses**: the agent tools installed there with their version, "latest" or "<version> available" in amber, and **Update** where the tool has an updater (`claude update`, `codex update`, `cursor-agent update`, `opencode upgrade`); it asks first, then runs the tool's own updater on that machine. Chats that are already running keep the version they started with.
- **Cache** (other machines): how much Burro has copied from it (last-seen chats, transcript copies, images and videos) with **Clear**.
- **New chat here** (opens the New chat sheet with that machine chosen; for this Mac, the current or main project), and **Open in Terminal** (this Mac: Terminal in the main project folder) or **Open SSH** (Terminal logged in to that machine: a normal interactive session with Burro's security options, but not the background check's timeouts, keep-alives or shared connection; no remote command is sent).

A machine that stopped answering is a quieter dashed card: since when, when Burro retries, how many of its chats can still be read from the local copy ("6 chats readable from the local copy"), its address and last error, **Retry now** and **Forget machine…** (asks, then removes it and what Burro copied from it). A paused machine says "Paused: Burro isn't checking this machine." with **Resume checks**. Below the cards, **Add a machine** takes an SSH address and opens the machine editor prefilled, where you confirm the name and port, and **Also on your tailnet** lists Tailscale devices you haven't added (if Tailscale is installed), each with **Add over SSH**. Cards share a row height and wrap to fewer columns in a narrow window.

The page only works while it's on screen: tool versions and Tailscale at most every minute (each machine's versions at most every ten minutes, npm's latest releases at most every six hours), the status lines every 5 seconds, and cache totals when the page appears, after a Clear and when machines change. Everything else on it comes from what Burro already holds.

### Notes window

**⌥P** opens Notes from any app (turn the shortcut off in **Settings → General → Open Notes with ⌥P from any app**; the menu bar's **Notes** item and Home's Notes card open it too). It floats over every app and Space without switching away from what you were doing; ⌥P again, Esc or ⌘W hides it, and it reopens on the note you had.

The first line is the note's title. Type `- [ ] ` or press **⇧⌘L** for a checklist: click a box to tick it, Return adds the next item, Return on an empty item ends the list, and ⌫ right after a box turns the line back into text. `- ` makes a bullet and `# ` a heading. Everything saves as you type, to `notes.json` on this Mac.

- **⌘P** browses notes: type to search, ↑↓ and Return to open, pin or delete from the row (delete asks twice). Pinned notes stay on top, the rest by when you last opened them.
- **⌘K** lists every action with its shortcut: New Note ⌘N, Duplicate ⌘D, Send to Orchestrator ⌘J (puts the note in the Orchestrator's composer and opens it), Pin ⇧⌘P, Go Back ⌘[ and Forward ⌘], Toggle Checklist ⇧⌘L, Find ⌘F, Copy as Markdown ⇧⌘C or Plain Text, Add Open Items to To-dos, and Delete Note.

### Today page

### Activity tracking

Burro can track where your time goes, entirely on this Mac. It is **off** until you press **Turn on** on the Today page's **Activity** card. It records only while Burro is open, so turn on **Settings → General → Open at login** (or **Open Burro at login** in the Activity **⋯** menu) to have it start with your Mac, quietly and without the window; the switch shows macOS's own login-item status, and if macOS asks for approval, **Open Login Items…** takes you to System Settings › General › Login Items. It records only the frontmost app, its window title and, in Safari, Chrome, Arc, Brave, Edge and Firefox, the site's host (`dashboard.stripe.com`, never the path or query). Arc keeps its accessibility tree empty until an app asks for it, so when Arc (or Chrome, Brave or Edge without a readable address field) comes to the front, Burro asks it once per launch to build that tree (`AXManualAccessibility`) and then reads only the page address of the window's web area, keeping the host. Building the tree costs the browser some CPU and memory while it runs; Burro reads no more often than before. To turn this off, switch off **Settings → Activity → Read the site in Arc and Chromium browsers** (it applies at once; those browsers then fall back to window titles). No screenshots, no text recognition, no AI, no keystrokes, and nothing is sent anywhere.

- **The day ribbon and the List view**: once tracking is on, the Today page's ribbon shows your blocks on its **You** lane (see [Today page](#today-page)). Switch to **List** for the vertical **timeline**, which has one block per stretch of activity: tinted by category, with the app's icon, a one-line title and its time range. It starts at the hour of the day's first block and ends at the last block (or now); an idle gap longer than 45 minutes is a thin **Idle · 2h 10m** divider instead of empty space (hover for its range), and shorter gaps keep their length. **Idle** means Burro was recording and you were away (no input; sleep and a locked screen count as away too). A stretch of 5 minutes or more when Burro wasn't recording at all (closed, paused or turned off) is a separate, fainter **Not recording · 2h 10m** divider wherever it falls, before the first block, between blocks or after the last; a day that opens with one starts at 0:00. Days from before Burro kept this record, and imported days, show no Not recording dividers. Time in one category with gaps under 5 minutes is one block; three or more short turns in a row (each under 10 minutes, such as Claude, Arc, Claude, Arc) are one **Switching between Claude and Arc** block; anything under 5 minutes folds into its longer neighbour (Private time never folds either way); blocks with under a minute of time aren't drawn (their time still counts). A block is titled by its main app (over 60% of its time) and that app's most-seen site or window title, such as "Xcode · ActivityLog.swift" or "Arc · github.com", never repeating the app ("Claude", not "Claude · Claude"; a trailing " - Slack" naming the app is dropped). Private blocks say only "Private" and the app. Titles come only from the app names, cleaned titles and hosts already recorded (no AI). Short blocks get a minimum height and the hour lines stretch with them; on wide windows the hours stretch further so the timeline fills the card beside it. Today opens at "now". Beside the timeline at a matching height (below it on narrow windows; on a short day whose timeline would leave it mostly empty, the timeline keeps its own height and this card is one row beneath it): **Your day so far**, with a donut of categories and the total, the apps and sites with the most time (only those with a minute or more), the day's focus stretches on a strip (a stretch is non-Break time that idle time or a break under 2 minutes doesn't end; the longest is highlighted) and what Break went to. The lock screen, login window, screen saver and system password prompts aren't activity: Burro records nothing while one is in front, and drops any such time already stored. The day arrows work for past days.
- **Home**: while tracking is on, Home's right column shows a **Today so far** card: **Recording** or **Paused**, focused of tracked time, a thin strip of the day's categories and, when there is such time, "Agents worked 2h 40m while you were away" (worked out on this Mac, as on the Today page). Click it to open Today. It reads today's file when Home appears and then every 2 minutes while Home is on screen (the away figure refreshes with it); with tracking off it isn't shown.
- **Window titles and sites** need macOS's Accessibility permission. Without it Burro still counts time per app, and the card shows **Allow…**, which asks macOS once and opens System Settings → Privacy & Security → Accessibility. Burro only asks when you click.
- **Pause** stops recording until you press **Resume** (it stays paused after a restart). The **⋯** menu also has **Turn off**, **Away after** (2, 5 or 10 minutes without input before you count as away; 2 by default, applied at once), **Open Burro at login**, **Delete this day…** and **Delete everything…** (each asks first; delete everything keeps your category rules).
- **Privacy rules**, applied before anything is stored: password managers and credential apps (1Password, Bitwarden, Dashlane, LastPass, KeePassXC, Keychain Access, Passwords, System Settings and similar) count as **Private** time with no title. Private and incognito windows (recognised by their window title or toolbar label) keep no title or site. Banking and payment sites (a built-in list such as boursobank.com, boursorama.com and paypal.com, any host with a bank word in it, plus sites you mark) keep no title and show as **Private**. Every title is cut to 120 characters, and email addresses, IBANs and runs of six or more digits (card numbers, account numbers, codes; spaces and dashes between them allowed) are replaced by `[email]` and `[number]`. Web addresses in a title lose everything from `?` or `#` on, and long runs of mixed letters and digits (24 or more characters, such as API keys) become `[token]`.
- **Categories** are simple rules: Build, Agents, Design, Analytics, Comms, Docs, Browsing, Break, Private and Other. The first match wins: Private, a site rule of yours, a built-in site, an app rule of yours, a built-in app, a word in the title, any other web page (Browsing), then Other. Site rules cover subdomains. Right-click a timeline block or an app or site row to change its category (it applies to past days too) or to **Treat it as private**, which also rewrites the days already stored.
- **Cost**: it reacts to app switches and window changes rather than polling. A check every 30 seconds notices when you've been without input for the **Away after** time (two minutes unless you pick 5 or 10), and idle time starts at your last input. While recording, a 30-second heartbeat (and waking or unlocking) extends the day's record of when Burro was recording. Only your own input (keys, clicks, scrolling, moving the mouse) ends idle time: apps an agent brings to the front while you're away aren't counted. While you're away the check runs every 5 seconds, so your return is noticed quickly. Sleep, screen lock and switching users stop it. A window that renames itself constantly is read at most every five seconds, flicks under five seconds fold into their neighbours, and the file is written at most every 30 seconds.
- **Storage**: `~/Library/Application Support/Burro/Activity/` (owner-only), one `YYYY-MM-DD.jsonl` file per day (at most 4 MB) with start, end, app, bundle id and the cleaned title and host, and beside it a `YYYY-MM-DD.coverage` file (owner-only, at most 64 KB) holding only the start and end times of when Burro was recording that day: from when recording starts (tracking on, not paused, Burro open) to when it stops (pause, turn off, quit), so a crash loses at most the last 30 seconds. Deleting a day or everything deletes its coverage file too. Days older than 365 days are deleted at launch and once a day. Your rules are in `rules.json` in the same folder. Activity never goes into the orchestrator's snapshot, `burro-mcp` (its file tools refuse Burro's data folder), triage's input, remote machines or logs.
- **Importing Dayflow history** (one time): `burro-inspect --activity-import-dayflow --dry-run` reads `~/Library/Application Support/Dayflow/chunks.sqlite` read-only and prints what it would write; drop `--dry-run` to write it (`--database <path>` and `--activity-dir <path>` point it elsewhere). Each Dayflow card becomes one timeline block with its own title (scrubbed like window titles) and category: Engineering / Product → Build, Distraction → Break, Data & Insights → Analytics, Research & Strategy → Docs, Communication → Comms, System and anything else → Other; Idle and deleted cards are skipped; Personal cards, banking or private sites, password managers and titles mentioning a bank or a private window become Private with no title. Your own site and app rules still win over an imported category. A day that already has tracked time keeps it, and imported time on that day stops where tracking began. Running it again replaces what it imported before, and it prints only counts and hours, never titles, sites or apps.

### Usage limits

Open **Usage** in the notch for a compact remaining-limit summary, including Claude's separate **Fable weekly** quota when reported. The arrow opens the desktop **Usage** page. Burro connects directly; it never reads, launches, or requires CodexBar.

The desktop **Usage** page (⌘7), top to bottom:

- The title with one sentence on what runs out at this pace (or "At this pace every limit lasts until it resets." only when every window is known to last until its reset; otherwise it names only the limits that do) and today's local tokens on this Mac, with **Refresh** and **Usage settings**.
- A card per provider: its name, plan, account and where the reading comes from; the **Account** menu (**Sign in / switch account…**, **Choose existing profile…**, **Use default account**, and for Claude **Allow Claude Keychain access…**); when it was read (**Stale** after ten minutes); any problem with its action (**Connect Claude**, **Sign in…**, **Refresh**); then each limit as a wide meter with what is left (or used, per Usage settings), a tick where even pacing would be, the reset, and the forecast. Extra usage, reset credits, product shares and the Claude Code fallback caveat follow, then **Usage dashboard** and **Service status** links and **Quota history** on request. Each card ends with **Local history (30 days)**: collapsed until you open it, it reads this Mac's logs for that provider only when opened (**Load local history**) or refreshed (**Refresh history**), and shows a daily chart by **Tokens** or **API value** and the usage by model (**Models · N**); Burro remembers which of these sections are open.
- **Today by project** (Home's project activity: named projects, then "Other folders") and **Today by model**, side by side, then **Last 7 days** as a strip of daily tokens. These are this Mac's own Codex and Claude logs, with an estimated API value at reference rates, never a bill; the caveats (priced coverage, partial scans, other accounts' logs, remote work, Grok) stay visible.
- **Orchestrator budget**: today's triage runs of the daily cap (with why triage is paused or off), what the Orchestrator's runs cost today as Claude Code reports them, and the models triage and questions run on, with **Settings**.

Below about 900 points the paired cards stack. While the page is on screen it refreshes provider limits when it opens and rescans the seven days of tokens, today's project activity and the Orchestrator's runs log at most every 90 seconds; nothing polls while it is hidden, covered or closed.

**Forecasts** are an explicitly linear guess, always worded "at this pace": the share of the window used, divided by the share of its time gone, extended to the reset. There is no forecast when the reading is stale, when the percentage, reset time or window length is unknown, or when the reset has passed without the refill being reported; in the first 30 minutes or 5% of a window (whichever is longer) it says it is too early. 0% left reads "Used up until reset".

**Account selection matters.** Quotas belong to the account shown on the card, across all its machines. Claude Code can be signed into a different account from Claude Desktop, your browser, or CodexBar. Different totals are then expected. Use **Account → Sign in / switch account** to run the provider's official CLI login in Terminal (after confirming that this changes the coding app's selected account), complete browser authentication, then refresh Burro. Burro does not enter credentials or copy another app's token cache. **Choose existing profile** reads an already configured profile folder; **Use default account** restores the default. Custom Claude profiles must contain their own `.credentials.json`; they never fall back to the default Keychain account. No remote credentials are imported.

- **Codex:** the installed desktop app or CLI provides account metadata and limits through its short-lived app-server connection. Both current `codex-cli/bin/codex` packages and older bundled CLI layouts are supported before standalone installs. No chat, prompt, or model request is sent. API-key-only accounts do not expose subscription quotas. Additional quota buckets remain separate. ### Done and unread status

Burro reads the provider apps' saved unread markers on this Mac. A successful Codex completion event, or an idle Claude desktop session with completed turns, must also be present. Codex internal sub-agent/guardian runs never produce Done notifications, even if they retain unread markers. Live workers still appear as working or needing input. Codex rows prefer the app's saved display name over the original prompt. Working, scheduled, needs-input, unknown, and stale-remote states take precedence. Clicking a row opens the provider; Burro waits for its saved read marker to clear on the next local refresh. It does not mark chats read itself or use a recent-completion timer. Done is separate from worktree safety: an open idle process still keeps its worktree in use.

Codex stores read state per account and execution host in `.codex-global-state.json`. Burro selects the account from the newest thread with creator identity metadata (or the sole saved account on older installations), never unions account histories, and ignores legacy migration snapshots. Switching accounts without creating an attributed thread can leave that selection behind; missing/ambiguous schemas show a visibility warning. The unread-status reader does not access authentication files or tokens.

Claude's `epitaxy-unread-v1` preference is read from its Chromium Local Storage, including manually unread IDs. The reader follows the current LevelDB manifest, sequence numbers and deletion markers, validates checksums, and reads only the relevant indexed blocks. It does not open or lock the provider database. Records in the live log are read the way LevelDB writes them, including ones that start right at the edge of a 32 KiB block, and the unfinished end of a log being appended is ignored rather than treated as damage. Missing registry/session metadata can prevent a Done badge; unsupported or changing storage fails closed and is retried on the next refresh. The result, or a failure, is reused while every database file keeps the same size, identity and modification time, so an unchanged store is parsed once; Codex's unread list is likewise reused while `.codex-global-state.json` and its `state_*.sqlite` files (with their WAL) are unchanged. A read-state failure shows as a notice but doesn't keep agent checks on the 3-second cadence. The format reader follows [LevelDB tables](https://github.com/google/leveldb/blob/main/doc/table_format.md) and [logs](https://github.com/google/leveldb/blob/main/doc/log_format.md).

Remote SQLite reads can use a stable, journal-free checkpoint when read-only WAL access is unavailable; a changed checkpoint or live journal cancels that fallback. Remote hosts return completion metadata; this Mac applies its own unread list using Codex thread UUIDs and Claude bridge IDs. Local unread IDs are never sent over SSH. Remote Codex completion history shares the existing 2,000-row/inspection-time limits; unread results beyond that coverage may be missing. Another laptop's `local_` Claude ID is never treated as a local read marker. Offline results become Last seen, not Done.

- **Vitals**: CPU (use, load and cores), **Memory pressure** (used of total), **Swap** and **Disk** (free space including purgeable space), each with its value, a one-word verdict such as **Fine**, **Busy**, **Under pressure** or **Filling up**, and a sparkline of the samples taken while a Mac view was on screen (kept in memory only; nothing is sampled for it). **Refresh** samples again.
- **Left running** in the main column. The side column shows the [Keep awake](#keep-awake) card, **Top by agents** when your agent chats are running processes (a process belongs to a chat when the chat's agent process is its ancestor; nothing is guessed from names), and **Busiest now**, your busiest processes, always.

It samples only while one of those views is on screen: system counters every five seconds, the process list every 15 seconds, and disk space every minute. A covered, minimized or hidden window, or a sleeping display, pauses it.

**Left running** lists things that usually outlived the work that started them. Each row shows what it is and where, **Why it’s flagged** (with the chat it belongs to when Burro can tell: under that chat's agent process, or in a Claude chat's temporary folder; click to show the chat in Burro), how long it has run, its memory, and **Stop…**:

- **Still busy:** a process outside any app still using at least 25% of a core after an hour of CPU time.
- **Long-running watcher:** a test runner, bundler, or `tail -f` running for over two hours. Jest and Metro worker pools count toward whatever started them; they are listed alone only after that parent exits. Memory figures are physical footprint, the same measure as Activity Monitor.
- **Idle server:** a process listening on a port with no open connections for over 12 hours.
- **Agent script:** a script started from a coding agent's temporary folder over six hours ago.
- **Orphaned:** a process outside any app whose parent exited at least an hour ago.
- **Headless simulator:** a booted iOS simulator with no Simulator window open for over 30 minutes.

Apps, macOS services, common background tools (watchman, syncthing, ssh-agent and similar), open Claude/Codex sessions, and helpers an app or agent started directly are never listed. **Stop…** asks first, then sends a normal quit request only if the process still has the same start time and executable; if it ignores that, the action becomes **Force Quit…**. **Shut Down…** runs `xcrun simctl shutdown` for that simulator. **Ignore** hides that tool in that folder until you choose **Show N ignored**. The notch tab only shows a summary; actions stay in the desktop page.

### Keep awake

The **Keep awake** card on Mac Health (also the menu bar's popover, with its clock menu for 1, 2 or 4 hours or until you stop, **Stop keeping awake** and the **While agents work** switch, and **Settings → Machines**) keeps this Mac from sleeping. It says whether the Mac is kept awake and why, and has one segmented control: **1 hour**, **2 hours**, **4 hours**, **Until I stop** and **While agents work**. **Stop** ends a timed request (While agents work stays on if it was).

- **1 hour / 2 hours / 4 hours / Until I stop.** Stays awake for that long, or until you click Stop.
- **While agents work.** Stays awake whenever a Codex or Claude chat on this Mac is working (the Orchestrator included), then for the time you pick under **After the last chat finishes, stay awake for** (**No extra time**, 5, 15 or 30 minutes) in case another turn starts. Chats on other machines don't count.

An open lid stays awake through an idle-sleep assertion Burro holds, with no password; it ends the moment Burro does. A closed lid needs `pmset -a disablesleep 1` (the same flag as [NoSleepBar](https://github.com/EdgarHnd/nosleep)):

- **Allow…** (or **Settings → Machines → Allow Without a Password…**) asks for your administrator password once and installs `/etc/sudoers.d/burro-keep-awake`, allowing exactly `/usr/bin/pmset -a disablesleep 0` and `… 1` without a password, checked with `visudo` first. With it, both modes cover a closed lid and start and stop on their own. **Remove Permission…** deletes the file (not while a lid-closed session is on). A rule you installed with NoSleepBar works too.
- Without it, picking a duration shows the administrator prompt; cancel it and only an open lid is covered (**Include closed lid…** asks again). **While agents work** never prompts on its own, so without the permission it covers an open lid only.

Each lid-closed session runs a small shell watchdog that turns sleep back on when you stop or the request ends, when the agents are done, 30 seconds after Burro quits or crashes (a relaunched Burro, such as after a rebuild, takes the session over instead), when Burro hasn't checked in for 15 minutes, or on battery at 10% or less (plugging in resumes it). The **Lid closed** tag and the green dot on the sidebar's Mac Health row show a session is on; the notch **Mac** tab shows a line while the Mac is kept awake.

If sleep is turned off with no Burro session (left by a session whose watchdog was killed, or set by another tool or a `pmset` command), the card says so with **Turn sleep back on**. Burro turns its own leftover back on by itself when it has the permission; it never changes a setting another tool made unless you click.

## What the labels mean

Activity and cleanup answer different questions: **Inactive** means no observed live use; **Ready to remove** means Burro can preserve the folder in Trash while keeping its commits on a verified local branch.

| Cleanup status | Meaning and next step |
| --- | --- |
| **Ready to remove** | Clean tracked/untracked checkout, no attached live/idle/uncertain chats or processes, successful visibility checks, and a local branch contains HEAD. Moving the folder to Trash keeps that branch. |
| **Local changes** | Modified, staged, or untracked files need saving or discarding. The inspector and blocker sheet show filenames. |
| **In use** | Close the attached chats or processes before removing the checkout. |
| **Protected** | Primary checkout, protected branch, user protection, Git lock, pinned chat, or another registered worktree nested inside. |
| **Archive in Codex** | Use the chat's archive action for Codex-managed worktrees; Burro does not unregister them. |
| **Save commits first** | Detached HEAD has no verified local branch containing it. Create a local branch at HEAD first. A remote-tracking ref alone is insufficient. |
| **Git in progress** | Finish the Git operation or resolve its lock. |
| **Cannot verify** | Missing registration/folder, submodules, incomplete provider visibility, or failed Git inspection. Investigate the specific reason shown. |

These are point-in-time observations; processes can start after a scan. Unknown evidence never becomes ready. Ignored files (including environments and dependencies) do not prevent recoverable removal because the entire folder moves to Trash.

## Cleanup and recovery

On the Worktrees page, the trash button above the page (or the **Safe to clean** chip) shows only the checkouts cleanup allows; the chips, state column, details inspector and confirmation use the same readiness decision (the table's **Safe to clean** is the confirmation's **Ready to remove**). Use **Select safe ones** in a repository's header or **Select all safe to clean** in the bulk bar to tick eligible rows within the current search and filter, or tick rows one by one. **Clear** unticks them. **Move N to Trash…** (⌘⌫ when you aren't typing in a field) in the bulk bar and **Move to Trash…** in a row's context menu open the same batch confirmation; when every ready folder has been measured, it says how much space emptying the Trash frees.

**Code & commits** separately shows integration evidence and the local branch preserving HEAD. Inclusion in locally available `origin/main`, `origin/staging`, `origin/master`, `origin/develop`, or your selected comparison branch is recognized even when the selected base differs. A small, clean, non-merge history may also be recognized as equivalent patches, including a combined squash. Squash candidates are shortlisted by commit subjects and accepted only when stable patch IDs match. Complex histories, changed titles without a match, timeouts, or output limits remain **Integration not confirmed**; this is not a claim that the PR is open. Burro does not query GitHub or fetch refs automatically.

Use **Compare with** to choose the repository's integration branch. This affects integration context, not whether commits are preserved. **An unmerged or unpushed branch can keep its commits after its checkout is removed.** Burro never deletes that branch. Uncommitted changes, activity, protection, and uncertain inspection still block removal. The older conservative `assessment` in CLI JSON remains an advisory merge/publication assessment; desktop cleanup uses the explicit retention evidence in `facts` instead.

Choose **Move to Trash…** for an eligible checkout or **Show blockers…** for the exact reason a checkout is unavailable. One short confirmation lists every selected folder, its retained branch, and any blockers. Only eligible rows are queued; blocked or changed rows are skipped. Codex-managed paths or attachments must be archived from their chats in Codex instead, even if local changes are the first blocker shown.

Confirmation triggers a fresh scan, verifies the same registration/HEAD/branch, rechecks Git and activity, and verifies the retaining branch still contains HEAD. It then moves the **entire folder** to macOS Trash. Ignored files and symlinks stay in Trash; external symlink targets are untouched. The retaining branch is rechecked before removing only that missing-folder registration, without force or global pruning. Trash must be supported for the folder's volume. If registration cleanup fails or evidence changes after the move, the error gives the preserved location and leaves the registration for manual inspection. No automatic removal occurs. Confirmed batches execute one worktree at a time through these same checks.

After confirmation, queued rows and counts update immediately and the sheet closes. A nonmodal progress strip lets you keep browsing, stop work that has not started, or inspect details. The current filesystem operation completes even after **Stop remaining**. Failed and skipped rows return immediately; a pre-cleanup background scan cannot resurrect pending rows or overwrite the later result. Successful rows remain hidden until a fresh post-batch scan reconciles the list. The result strip retains per-item errors, Trash destinations, kept branch and full commit, and a **Show in Finder** action; there is no success alert to dismiss. Results live in memory until dismissed or replaced by the next batch. A failure after moving the folder reports its preserved Trash location rather than claiming it stayed at its original path.

To restore, create a new worktree on the retained branch (or at the full commit shown for a detached checkout), then copy needed local/ignored files from Trash into it. The `.git` pointer in the trashed folder references the removed registration; dragging it back alone does not repair that registration. Files occupy disk space until Trash is emptied. Emptying Trash is permanent. Fresh checks reduce but cannot eliminate races with other processes.

## Agent detection and limits

- **Codex:** opens the newest `~/.codex/state_*.sqlite` read-only; joins chat workspaces and worktree attachments; inspects existing writer locks without creating them; reads bounded 512 KB transcript tails for turn-start/completion events. Held writer locks plus events distinguish working from open/idle. Recent unfinished events without a lock are marked recent activity, not confirmed running. Missing/unsupported schemas produce a visible notice and prevent cleanup readiness.
- **Claude Code:** reads `~/.claude/sessions/*.json`, verifies the live executable, PID, and process start time, then uses its reported status plus bounded delegated-work checks for idle parents. Dead PIDs are inactive; uncertain or reused identities stay unknown. Unrecognized live status is unknown and protects the worktree.
- **Processes:** uses macOS libproc for same-user process working directories, including terminals and dev servers. The scanner and its descendants are excluded. A nested worktree owns its own activity instead of incorrectly attributing it to the main checkout.
- Provider formats are private implementation details, observed on this Mac in September 2026. Other versions can provide less detail; missing evidence is not evidence of safety. Other users' processes and hosts that have not been added to Burro are outside coverage. Legacy Claude versions without session registries rely on process evidence and show reduced coverage.
- Historical Claude sessions are limited to records retained in the local session directory; Burro does not crawl all old conversations. Codex history includes unarchived database records. The detail pane shows up to ten inactive records per worktree.
- Local checks wake on provider file changes and otherwise run about every 3 seconds while a chat is working, waiting or uncertain, and every 15 seconds when all chats are quiet and the file watcher runs (3 seconds without it). Pages redraw only when a chat or notice they show changed.
- Local session titles and filesystem paths remain in memory/UI (other machines' last-seen chats are kept in the remote cache; see [Other laptops and servers](#other-laptops-and-servers)). Burro persists selected roots, comparison refs, discovery preference, manual protections, notch preferences, explicit remote host configurations, New chat defaults, the Orchestrator's daily sessions and Burro's own per-chat titles, pins, hidden chats and seen marks in `local.burro.worktrees` UserDefaults. On first launch after the Grove rename, it imports only the four original preference keys from `local.grove.worktrees` once, without overwriting existing Burro values. CLI JSON contains titles/paths and should be treated as local data. No telemetry is sent. Configured remote hosts receive only Burro's fixed scripts over SSH.
